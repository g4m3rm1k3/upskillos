# A — From a Python script to Dice Duel

**Status: curriculum draft.** Return to the [path and teaching contract](../../cpp-games-learning-path.md). All paths below are proposed files inside the learner's `dice-lab/` project. Lesson codes are planning references, not published IDs.

Entry: the learner can run a Python script containing variables, a list, decisions and a loop. No knowledge of functions, classes, tests, build systems, probability or reinforcement learning is required. Exit: the learner can develop, test, train, evaluate and explain a terminal game distributed across purposeful C++ files.

The first learner-built success is a program printing a score. The first small game is playable before machine learning. The full target game keeps the current Dice Duel rules: race to 12; rolling 1 loses the unbanked pot; rolling 2–6 adds to it; banking a positive pot transfers it to the score; score plus pot reaching 12 wins immediately. A roll is supplied to the rule logic so tests can choose outcomes.

Before A01, teach [A00 — Can you beat an opponent that learned to play?](course-openings.md#a00--can-you-beat-an-opponent-that-learned-to-play). Show the finished game and its rules before installation. The learner makes a roll/bank decision, sees the consequences and chooses a personal feature goal. Each chapter below likewise starts by demonstrating the behavior it will add.

## Chapter A1 — A file becomes a running program

| Lesson | Problem and files | Concepts to teach through the edit | Independent challenge and evidence |
|---|---|---|---|
| A01 — Which program did I run? | Create `hello.cpp`, compile it, edit its greeting, run the old executable, then rebuild. Teach opening a terminal and identifying its current folder. | Source is text; a compiler translates it; an executable is the resulting program. Explain `#include`, `main`, braces, a statement, `;`, `std::cout`, newline and exit status across small steps. | Make a different greeting program without copying the example. Explain why the old binary ignored an unsaved edit. Check its output and require a successful fresh compilation. |
| A02 — A score is a value with a type | Add score arithmetic in `explore/types.cpp`; keep the first file working. | `int`, `double`, `bool`, `const`, initialization and assignment. Types determine operations; `1 / 6` and `1.0 / 6.0` differ. Explain bounded integers without introducing manual memory management. | Compute remaining points for several scores and a fractional ratio for several totals. A wrong integer-division implementation must fail a nonintegral case. |
| A03 — Input can fail | Write `explore/input.cpp` and read a score using a stream. Use the terminal for interaction, then replay input in a check. | `std::cin`, extraction, input failure and end-of-input. Read into an initialized variable; test success before using it. Define standard input/output/error and distinguish program input from shell commands. | Accept an integer and reject a word with a nonzero exit code. Tests cover zero, ordinary values and EOF. Do not equate extraction of a prefix with validation of a whole line; stricter command parsing comes later. |
| A04 — Decisions have boundaries | In `explore/decisions.cpp`, decide whether a supplied score reaches a target. | Comparisons, `if`/`else`, `&&`, `||`, `!`, short-circuit evaluation and inclusive boundaries. One operator per small experiment. Assignment changes a value; equality asks a question. | Report below/exactly/above target without sample-specific output. Tests exercise 11, 12 and 13 and a different target. Diagnose an off-by-one bug before fixing it. |
| A05 — Return a result to a caller | Build `points_needed` in `explore/functions.cpp`; call it for two players. | Function, parameter, argument, return type, local variable and call stack. Trace `points_needed(4, 12)` returning 8. A function that prints is not interchangeable with one that returns. | Write a related `can_bank` function from a contract. Check several callers and use its result in a branch. Explain what is copied into each parameter and why names can differ at the call site. |

Gate: independently create, compile and run a file; explain the build/run distinction; repair a compiler error using its file and line; trace an unfamiliar function call. Recover with another tiny program, not more build flags.

## Chapter A2 — Values become game state

| Lesson | Problem and files | Concepts to teach through the edit | Independent challenge and evidence |
|---|---|---|---|
| A06 — Change the caller or change a copy? | Compare two functions in `explore/references.cpp`, one taking `int`, one taking `int&`. | Scope, value copy, reference, alias and `const` reference. Trace addresses conceptually with named storage boxes; do not imply references extend an object's lifetime. | Implement a score transfer that changes the caller and resets the pot. Test two independent scores. A copy-only implementation must fail; a read-only query must accept const data. |
| A07 — Two players, two independent objects | Replace loose score variables with a `Player` struct in `explore/players.cpp`; then store two in `std::array`. | Struct, object, member, member access, initialization and value semantics. An array stores a fixed number; a vector can grow. Explore a tiny vector separately before collecting a history. | Add a second player's score without altering the first. Test copying a player, then changing the copy. Diagnose an out-of-range index without relying on undefined behavior. |
| A08 — A turn has named choices | Use `Action` and a short list of predetermined dice in `explore/turns.cpp`. | `enum class` names a restricted set of values. Teach a range-based loop, index loop, `break` and `continue` in separate traces. Define an accumulator with a pot trace: 3, 5, 1 gives 3, 8, 0. | Stop processing rolls at the first bust. A trailing 6 must not appear in the pot. Test empty input, no bust and bust-first. Explain why `continue` gives a different result. |
| A09 — A test can catch your mistake | Write the first comparison-based `tests/score_tests.cpp`, then replace repetitive failure handling with assertions. | Specification, expected/actual value, assertion, unit test, regression and boundary case. Teach a failing test before a passing one. Explain why disabled assertions cannot validate a release test suite. | Write a test that detects banking by replacement instead of addition. Author review runs that test against both implementations. Passing tests alone do not prove all possible inputs are covered. |
| A10 — Protect a score with a class | Introduce `Score` in `explore/score_class.cpp` after demonstrating unrestricted negative points in the struct. | Class, public interface, private member, method, encapsulation and invariant: the score never decreases through banking. Explain class/struct default access; neither keyword alone produces good design. | Create two score objects, reject a negative bank and preserve both prior totals. Checks use varied sequences and state snapshots. See the [worked specification](lesson-specimen.md) for the intended teaching depth. |

Gate: explain the difference between two objects, two names for one object and a copy. Implement and test a small behavior without a supplied method body. Do not introduce inheritance to represent players.

## Chapter A3 — Classes with responsibilities

| Lesson | Problem and files | Concepts to teach through the edit | Independent challenge and evidence |
|---|---|---|---|
| A11 — Begin in a valid state | Give `Score` a constructor and add a `Rules` value with a target in `explore/construction.cpp`. | Constructor, member initializer, default value and construction failure. Separate validation from mutation. Teach method arguments before constructor overloading; avoid implicit conversion surprises by introducing `explicit` with a one-argument example. | Accept a valid starting score and reject a negative one. Prove a failed creation never returns an invalid object. Explain why assigning private members later leaves a dangerous gap. |
| A12 — Own the game, expose a snapshot | Grow `explore/game_model.cpp`: `Game` contains scores, turn and pot; a `GameSnapshot` contains the information a caller may inspect. | Composition, const methods and a read-only interface. A returned value is a copy; it cannot modify the original. Teach `this` as the current object only when resolving a naming collision. | Add a query that reports the current player's total without leaking a mutable reference. Tests modify a snapshot and confirm the game is unchanged. Explain the cost and benefit of copying this small state. |
| A13 — Invalid input is not a lost game | Separate rejected input from game outcomes in `explore/errors.cpp`. | Error code versus exception, `throw`, `try`, `catch` and standard exception types. Expected bad input can be a normal result; a violated internal contract requires clear failure. A failed operation preserves the old state. | Reject an impossible die face without switching turns or changing the pot. Test 0, 7 and a valid face. The learner explains the difference between a rejected move and a legal bust. |
| A14 — Objects have lifetimes | Use nested scopes and a tiny tracing type in `explore/lifetime.cpp`; then write and close a file with a standard stream object. | Constructor/destructor order, resource, ownership, borrowing and RAII. Teach pointers, `nullptr`, address-of and dereference through valid objects before any library handle is seen. Use a small unique-owner example to introduce deleted copy operations; defer custom move support until B. | Predict destruction order and make file contents available before reading them. Identify a dangling reference in code without executing it. Check a nested-scope trace and explain why a borrower must not delete the owner. |
| A15 — A header is a promise | Extract `include/dice/Score.hpp` and `dice-lab/src/dice/Score.cpp` from already-working code, one file per step. | Declaration versus definition, header, include guard, quoted include, namespace and qualified name. A translation unit is a source file after preprocessing. `#include` supplies declarations; it is not Python module execution. | Move one method definition into the source file without changing its contract. Compile two callers. A duplicate or missing definition exercise teaches distinct compiler/linker diagnostics. |

Gate: design a small class, name its invariant, identify its owner and put its interface/implementation in separate files. Recover with `Score` before designing `Game`.

## Chapter A4 — A project you can build and change

| Lesson | Problem and files | Concepts to teach through the edit | Independent challenge and evidence |
|---|---|---|---|
| A16 — The linker needs the implementation | Build `apps/score_demo.cpp` and `tests/score_tests.cpp` against the same score source using explicit compiler commands. | Compilation versus linking, object file, include search path and multiple `main` functions. Explain every new command argument. Each executable has one entry point; shared rules contain none. | Repair a command that omits the implementation source. Teach Git working tree, diff, staging and local commit as a separate small sequence before recording this milestone; no remote account is required. Verify both executables. |
| A17 — Give the build a dependency graph | Type `CMakeLists.txt`; make a `dice_rules` library target, demo target and test target. Migrate the tested `Game` into matching include/source files. | Target, source directory, build directory, configure, build, dependency and CTest. Explain public/private include requirements with two callers. Do not paste a generic CMake template. [Official CMake tutorial](https://cmake.org/cmake/help/latest/guide/tutorial/index.html). | Add a second test target independently. Build from a fresh folder and run tests. A clean build must work without stale objects. Write a short README describing the folder roles and exact commands used. |
| A18 — Complete the deterministic rules | Implement `Game::apply` and pure legality queries in `dice-lab/src/dice/Game.cpp`, keeping the die value an input. | State machine, transition, legal action, terminal state and invariant. Draw the transition trace before coding. Test a win before passing the turn; represent no winner distinctly. | Add cases for bank, bust, exact win, overshoot, both seats and post-game input. Match the existing Dice Duel rules. Feed the same recorded actions and rolls through old and new implementations during migration. |
| A19 — A playable terminal duel | Create `apps/terminal.cpp`, a command parser and a seeded die source. Build a fixed opponent with a simple threshold. | Event/input loop, line parsing, deterministic pseudo-random sequence, seed, engine versus distribution, separating policy randomness from dice. Teach whole-line validation and EOF explicitly. | Reject a malformed command without consuming a die or switching player. Replay a predetermined match and quit cleanly. Same seed means reproducibility on the documented build, not an identical distribution implementation across all platforms. |

Gate: play a complete terminal game, add a rule test from a reported bug, and explain how the same model serves tests and human input. This is a usable stopping point before ML.

## Chapter A5 — Decisions become learning examples

| Lesson | Problem and files | Concepts to teach through the edit | Independent challenge and evidence |
|---|---|---|---|
| A20 — Risk, averages and a baseline | Enumerate the six outcomes in `explore/risk.cpp`; record a fixed opponent's results. | Probability as favorable outcomes divided by total equally likely outcomes, expected value as a weighted average, sample frequency versus exact probability. Introduce notation after computing real numbers. | Compute expected pot change for another pot. Explain why maximizing one-roll points is not automatically maximizing match wins. Check exact enumerated arithmetic; random samples use justified tolerances. |
| A21 — Whose action gets the reward? | Build `Environment` and `Transition` using `Game` in `dice-lab/src/learning/Environment.cpp`. | Agent, environment, observation/state, action, reward, episode and transition. A nonterminal successor belongs to the learning player after the fixed opponent's intervening moves. Discuss what information makes this chosen state sufficient. | Trace a bank followed by the opponent winning. Correct reward is -1 for the agent. Test agent wins, opponent wins, unfinished successors and preservation of an input snapshot. |
| A22 — Store one estimate per choice | Build `QAgent` and its table in `include/learning/QAgent.hpp` and the source counterpart. | Action value, array row, vector storage, `using` alias, template arguments through concrete container types, index encoding and checked lookup. Work `(2 * 12 + 3) * 12 + 4 = 328`. | Decode an index and prove no collisions for the admitted nonterminal states. Illegal bank values never participate in a maximum. Test bounds and aliasing; no mutable table access in the public play interface. |
| A23 — Try an action you do not yet trust | Add epsilon-greedy action selection after a two-action probability experiment. | Exploration, exploitation, epsilon, uniform choice and tie-breaking. For epsilon 0.2 and two legal actions, the uniquely best action has probability 0.9. | Implement a deterministic choice at epsilon zero and fair selection for tied values. Tests cover a forced roll and statistical smoke bounds; a frequency test does not prove the generator is random. |
| A24 — Learn from a final result | Add only terminal updates to `QAgent::learn`; use an explicit old value, target and error trace first. | Estimate, prediction error and learning rate alpha. With old 0.2, reward -1 and alpha 0.5, new value is -0.4. Teach floating-point comparison tolerance. | Update a different cell and show that its neighbor is unchanged. A terminal successor may contain deliberately unusable coordinates: passing proves the update never looks it up. |
| A25 — Learn before the game ends | Extend the target to reward plus discounted best legal successor value. | Discount gamma, bootstrap, Q-learning and behavior versus target policy. Define the distinction from following the next sampled action without introducing another algorithm implementation. | Work a nonterminal update by hand, then implement it. Reject maxima over illegal actions and copied-cell updates. Explain why alpha and gamma cannot be exchanged. |

Gate: with code hidden, compute a terminal and nonterminal update; explain whose reward is used; diagnose a policy selecting an illegal bank. No neural network prerequisite is introduced.

## Chapter A6 — Train, evaluate and preserve what was learned

| Lesson | Problem and files | Concepts to teach through the edit | Independent challenge and evidence |
|---|---|---|---|
| A26 — Many games, controlled experiments | Add `TrainingSession` and `apps/train.cpp`; coordinate reset, select, transition and learn. | Episode loop, exploration schedule, separate random streams, seed recording and step guard. Teach numeric casts before dividing episode integers. A guard aborts the experiment; it does not invent a loss. | Alternate starters and implement a different exploration floor. Test repeated runs on the same build, no updates without an agent decision, and no fabricated terminal reward after a guard. |
| A27 — Better than what? | Create `apps/evaluate.cpp` with a frozen model and held-out seeds. | Baseline, evaluation protocol, sampling uncertainty, sample size, training-seed variation and opponent shift. Introduce standard error through repeated sample rates before its formula; report assumptions and per-seat results. | Detect accidental learning during evaluation by comparing every table value before/after. Compare against another fixed opponent. Grade the experiment and report, never a lucky win-rate threshold. |
| A28 — Save a model you can safely restore | Type `ModelStore` in separate header/source files and create `tests/storage_tests.cpp`. | Serialization, schema/version, precision, validation, temporary candidate and commit-on-success. The file records rules and table shape, not just numbers. Explain stream lifetime and write failures. | Reject truncated, incompatible and malformed files without replacing a working model. Test numeric round-trip and trailing garbage. State clearly whether a save is atomic; do not claim it without implementing and testing a replacement strategy. |
| A29 — Play against your frozen agent | Create a terminal application mode that loads a saved agent and displays legal choices and estimates. | Application composition, model versus UI, configuration and command-line arguments. One executable trains; another plays. Introduce parsing options before using them in scripts. | Add a replay option and preserve the trained table during play. Prove training can run without terminal input and play can run without invoking a training session. |
| A30 — Someone else builds your project | Finish `README.md`, `.gitignore`, build/test instructions and a transfer challenge. | Debug/release configuration, reproducible build, generated artifact, version control milestone and limitation report. Explain the difference between copying source and distributing an executable plus runtime dependencies. | From an empty build folder, compile, test, train and play. Independently add a match-history summary with tests. Explain which parts change if the target changes, including saved-model compatibility. |

## Class and file decisions to defend

| Type or function | Owns or computes | Why it exists; what it must not do |
|---|---|---|
| `Score` | A banked score in the class-learning exercises | Demonstrates an invariant; later decide whether `Game` should instead store simple private integers. Keep or remove it with a reason. |
| `Rules` | Target and rule configuration | A value, not a global mutable settings object. Do not expose options the model format cannot describe. |
| `Game` | Valid scores, pot, turn and winner | Enforces transitions; does not read input, generate random rolls or draw. |
| `GameSnapshot` | A copy of observable state | Lets UI and tests inspect without bypassing the game's interface. |
| `Environment` | A game plus the fixed-opponent transition boundary | Produces correctly attributed training transitions; not a second copy of the game rules. |
| `QAgent` | The value table | Selects legal actions and applies explicit updates. Evaluation uses a read-only interface. |
| `TrainingSession` | Episode orchestration and random sources | Coordinates existing responsibilities; does not hide the learning equation. |
| `ModelStore` | Model read/write operations | Validates data. A stateless namespace of functions is acceptable if the learner can justify why no object state is needed. |

The chapter gate explicitly asks whether each class is necessary. “Real classes” means meaningful ownership and behavior, not turning every function into a class or building an inheritance tree.

## What must be verified before this draft becomes lessons

Use a fresh learner folder and run every named command. Review full-file targets as live incremental diffs. Every independent task gets normal, boundary and wrong-answer cases; at least one case must differ from the visible worked numbers. Tests must not accept printing all sample answers. Check copy/reference, invalid-state preservation and terminal bootstrap mutants specifically.
