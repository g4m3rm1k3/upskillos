# B — Make Dice Duel graphical with SDL3

**Status: curriculum draft.** Prerequisite: [A's terminal game and mastery gates](01-terminal.md). Return to the [whole path](../../cpp-games-learning-path.md). Proposed learner paths below extend the same `dice-lab/` repository; no replacement project or supplied game source is introduced.

The learner already understands C++ functions, classes, ownership and a small CMake project. They have never made a window. This part teaches SDL3 as a library providing platform facilities, while the learner writes the game application's structure. SDL's 2D Render API supports the simple drawing and textures required here; it is distinct from the shader-oriented GPU API in C. [SDL Render documentation](https://wiki.libsdl.org/SDL3/CategoryRender).

The first learner-built success is a window that can close. The final project draws dice, scores and available actions, animates a resolved roll, accepts keyboard/mouse commands and plays against the saved Q-agent. Training stays outside the interactive frame loop.

Before B01, teach [B00 — Turn your terminal game into a game you can see](course-openings.md#b00--turn-your-terminal-game-into-a-game-you-can-see). Demonstrate the completed graphical game, including animation, input and resize; explain why it reuses the learner's rules. Start every chapter with a short preview of its own visible result.

## Chapter B1 — A dependency and a window

| Lesson | Problem and files | Mechanism and vocabulary | Independent challenge and evidence |
|---|---|---|---|
| B01 — Read the dependency before installing it | Add a dependency record to `README.md` and a small SDL discovery target to the build. | Library, header, implementation binary, SDK, version, license, package and ABI. Show why a header alone cannot satisfy linking, and why compiler-compatible binary packages matter. Teach the selected package workflow from an empty machine profile. | Identify a wrong-major-version package from its headers and a missing runtime binary from the actual loader error. A fresh configure/build must identify the pinned SDL3 package and record compiler/generator details. |
| B02 — Initialize, check, clean up | Type `explore/sdl_start.cpp` using only SDL initialization, an error report and cleanup. | API signature, return value, SDL3's documented success convention, subsystem and diagnostic. Do not teach SDL2 return conventions by accident. Explain each include and any entry-point support header used by the selected setup. | Make initialization fail in a controlled unsupported-driver experiment where available; otherwise test the application's failure-reporting branch through an explicit seam. A normal run and a failure run must have distinguishable exit codes. |
| B03 — A window owns an external resource | Create `explore/window.cpp` and then a `Window` owner in `include/platform/Window.hpp` and its source. | Opaque handle, pointer to a library object, owning wrapper, constructor/destructor and deleted copying. Draw the SDL session → window lifetime dependency. Introduce wrapper behavior after the raw acquire/release sequence is understood. | Add a title/size option without allowing two owners of one handle. Check close-on-scope-exit and a negative compile test for copying. A compile test alone cannot prove a window appeared. |
| B04 — Read events instead of waiting for a line | Add an event loop to `apps/sdl_game.cpp`. | Event queue, polling, event type, tagged event data and quit request. Explain why blocking `std::getline` would stop the application processing window events. Teach the event's active data member before reading it. | Support both window close and Escape. Prove an unrelated event does not exit. A bounded smoke mode must close without human input; a separate manual check verifies the visible window. |
| B05 — Create a renderer and present a frame | Add a `Canvas2D` resource owner and clear/present calls. | Renderer, render target, frame, clear color, draw order and presentation. Explain RGBA channels with a solid-color experiment. Renderer lifetime depends on the window; both depend on initialized SDL. | Change a background through a key event. Verify event handling still works. Explain why drawing after presenting appears only on a later frame. Observe cleanup order and report API failures. |

Gate: from the README alone, build and open a window that responds and exits cleanly. Explain which layer owns each resource. Restore the terminal build after intentionally removing SDL from the graphical target: rules/tests must remain buildable.

## Chapter B2 — State becomes a picture

| Lesson | Problem and files | Mechanism and vocabulary | Independent challenge and evidence |
|---|---|---|---|
| B06 — Coordinates are measurements | Type `explore/layout.cpp`, then `include/ui/BoardLayout.hpp` and its implementation. | Point, rectangle, origin, axes, width/height and coordinate units. A window coordinate and a logical game coordinate may differ. Use numeric examples before any scaling formula. | Place two score areas with a specified gap. Unit-test rectangle positions for different logical sizes and inspect the actual frame. Do not accept one screenshot as evidence that resize works. |
| B07 — Draw every die face from data | Add a pip-layout function and `ui/DiceView`. | Data-driven drawing, normalized positions, a lookup table and a pure transformation from die value to shapes. Keep die sampling in game logic. | Independently implement a missing face and reject values outside 1–6. Check pip count, position symmetry and all six rendered faces. A repeated draw must not advance a random stream. |
| B08 — Read a snapshot, leave the model alone | Build `ui/BoardView` from `GameSnapshot` and layout. | Model, view, read-only dependency and separation of responsibilities. Introduce a small presentation struct only if it avoids embedding game rules in drawing. | Draw scores, pot and active-player emphasis from test snapshots. Assert rendering preparation leaves the original state unchanged. Every visual element must be traceable to a named model field. |
| B09 — Text introduces another resource | Start with simple diagnostic labels, then integrate SDL_ttf for a readable interface. Add a `Font` owner and text texture lifecycle. | Font, glyph, rasterization, cache and invalidation. Explain why recreating unchanged text every frame does unnecessary work. Teach the extra library setup separately from rendering code. | Update only the changing score label. Test the cache key and inspect fresh text after a font/size change. Record asset license and report missing fonts clearly. |
| B10 — Resize without moving the click target | Extend `BoardLayout` and the window event handling. | Logical presentation, aspect ratio, letterboxing, high-DPI pixel size and inverse coordinate mapping. Work one window-to-board conversion by hand before using the API. | Resize to a wide and a tall window; clicks must still align with buttons. Check boundary mappings numerically and verify on a high-DPI display when available. Mark unavailable hardware checks honestly. |

Gate: given an unfamiliar game snapshot, explain every shape on screen. Change layout without changing rules. Debug a coordinate conversion using numbers rather than moving rectangles until they look right.

## Chapter B3 — Input asks; the game decides

| Lesson | Problem and files | Mechanism and vocabulary | Independent challenge and evidence |
|---|---|---|---|
| B11 — Turn events into requests | Add `ui/InputMap` and a small `Command` value. | Input adapter, command, intent and validation boundary. A request to bank is not proof banking is legal. Translate events once and send the same intent from keyboard and mouse. | Map an alternate key without duplicating game transitions. Test event-to-command and command-to-game separately, including a rejected bank at pot zero. |
| B12 — A button has interaction state | Add `ui/Button` only after a rectangle needs hover/pressed/released behavior. | Hit test, focus, press versus release, disabled state and event repetition. A held key or mouse button must not execute a turn action every frame. | Implement a click cancelled by dragging outside. Test press-inside/release-outside, disabled input and repeated key events. Visually distinguish disabled state without relying on color alone. |
| B13 — Update and draw have different jobs | Extract `GameApp` to coordinate input, game and view. | Application loop, update, render, composition and dependency direction. Explain why a controller coordinates operations but must not become a second rules implementation. | Feed the same commands through terminal and graphical adapters and compare snapshots. An extra render between commands must not alter the match. |
| B14 — Animate a result already decided | Add `ui/RollAnimation` with elapsed time and a known final face. | Duration, elapsed time, interpolation, clamp and presentation state. The random roll is decided once; animation cannot resample it or change training outcomes. | Pause rendering or change frame rate and preserve the final face. Numeric tests cover start/middle/end and overshoot; visual checks verify the die settles. |
| B15 — A nonblocking opponent turn | Add an application phase enum such as awaiting input, animating and showing result. | Finite-state machine, phase transition, pending action and reentrancy. Introduce timing without sleeping the main thread. Dice Duel is turn based: explain why it does not need a physics timestep. | Ignore extra roll requests during animation and run the bot once per eligible turn. Check close/minimize events remain responsive while the bot or animation is active. |

Gate: reproduce a double-action bug, write a test and repair the responsible layer. Explain the difference between game state and animation state.

## Chapter B4 — A complete application

| Lesson | Problem and files | Mechanism and vocabulary | Independent challenge and evidence |
|---|---|---|---|
| B16 — Load the opponent at a boundary | Connect `ModelStore` and a read-only agent to `GameApp`. | Configuration, dependency injection through ordinary constructor parameters, recoverable loading failure and fallback. No service locator or global agent is needed. | Select a fixed opponent when a model is missing, with an explicit visible notice. A malformed file must not become a zero-filled “trained” agent. Check no learning calls occur during play. |
| B17 — Sound belongs to an event | Add a small `Audio` owner using a simple queued playback path and a supplied licensed sound. | Sample, sample rate, channel, audio format, buffer and latency. Keep callbacks/concurrent access out of the first audio implementation; teach them before adding such a design later. | Play one cue per accepted roll and none on rejected input. Test event emission separately from audible output. Handle unavailable audio with a clear muted mode that does not prevent playing. |
| B18 — Resources survive code changes | Consolidate the window, renderer, font, textures and audio ownership graph. Use `std::unique_ptr` with a custom deleter where its purpose is now concrete. | Smart pointer, custom deleter, move, moved-from state and rule of zero. Explain the tiny template/lambda syntax independently before using it in a resource alias. Do not add `shared_ptr` just to avoid deciding an owner. | Move a texture owner and prove exactly one release. Exercise partial initialization failures. Class-level and SDL-level destruction sequences must be distinguished. |
| B19 — Save a replay, reproduce a bug | Add a versioned action/roll replay file and deterministic replay runner. | Event log, replay, regression fixture and difference between command intent and accepted transition. A replay records actual dice, not just a seed whose distribution may vary across builds. | Reproduce a reported match from a file. Reject invalid actions and incompatible rule versions. Match every replayed snapshot between the terminal runner and GUI model. |
| B20 — Build an application someone can run | Add install/package rules and asset-path handling to the build and README. | Runtime dependency, working directory, executable-relative resources, packaging and smoke test. Teach the selected platform layout; do not assume running from the source root. | Launch the packaged app from another directory on a clean profile. Verify missing assets report useful errors. Check terminal tests remain independent of window/audio initialization. |

## Resulting structure and responsibility

These folders are added only when their contents exist:

```text
dice-lab/
  include/platform/   SdlSession.hpp, Window.hpp, Canvas2D.hpp, Audio.hpp
  src/platform/       matching implementation files
  include/ui/         BoardLayout.hpp, BoardView.hpp, InputMap.hpp
                      Button.hpp, RollAnimation.hpp, GameApp.hpp
  src/ui/             matching implementation files
  apps/               sdl_game.cpp
  tests/              layout_tests.cpp, input_tests.cpp, replay_tests.cpp
  assets/             font and sound data, with license/origin records
```

`SdlSession` owns initialization lifetime. `Window` owns one window. `Canvas2D` borrows that window while owning its renderer. A texture owner must be destroyed before the renderer it depends on. `GameApp` coordinates but does not implement scores, policies or raw drawing internals. `BoardView` borrows a canvas and consumes snapshots. The exact type boundaries are reviewed against actual needs; this is not a requirement to create a wrapper around every SDL function.

## Verification required during authoring

Each lesson has compiler/build checks and logic tests where meaningful. Graphical checks add a bounded application mode, reported backend/version, a screenshot or human observation and cleanup confirmation. Test close, resize, minimize/restore, invalid assets and initialization failure. Run at least one actual SDL renderer; a fake renderer verifies submitted intent, not the driver's output.

The implementation must pin and document compatible SDL3 and SDL_ttf versions, install steps and runtime deployment for each claimed platform. SDL3 API usage is checked against its documentation rather than an SDL2 snippet. Cross-platform validation remains a release task, not something established by this draft.
