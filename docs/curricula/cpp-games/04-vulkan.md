# D — Build and explain a Vulkan renderer

**Status: curriculum draft; native renderer not implemented or validated.** Follow the [authoring and Vulkan readiness gates](authoring-gates.md) before publishing executable lessons. Prerequisite: [C's graphics and SDL GPU renderer](03-gpu.md), including shaders, coordinate spaces, buffer layouts, ownership and submitted work. Return to the [whole path](../../cpp-games-learning-path.md).

This part rebuilds the graphics backend while preserving the game and scene-description contract. It is deliberately a graphics/software-engineering series. It does not introduce a new game, new ML algorithm and new graphics API at the same time.

Before D01, teach [D00 — Build the machinery that makes the frame happen](course-openings.md#d00--build-the-machinery-that-makes-the-frame-happen). Show the working Vulkan game and annotated frame/resource inspection. Explain the payoff of understanding explicit control without promising better visuals or performance merely from changing APIs. Each chapter starts with the concrete capability it will add.

The learner types every application-owned wrapper, allocation routine, shader change, build rule and test. Vulkan's repeated structure fields are explained through the question each answers: which resource, what usage, whose memory, which dependency? No step says “paste the boilerplate.” Before the first triangle, successful lessons produce capability reports, verified resource lifetimes and a cleared window. They are runnable milestones, not silent setup pages.

## Scope and decisions to validate during implementation

Use the direct Vulkan C API from C++ for the core teaching path. This makes handles, output parameters and result codes visible. Build small C++ owners only after the underlying acquire/release operation has been traced. Do not introduce Vulkan-Hpp templates, a bootstrap library or a large prewritten engine as unexplained scaffolding. Later comparisons may examine those alternatives with the same contracts.

Draft rendering baseline: Vulkan 1.3 with dynamic rendering and synchronization2 queried and enabled, one graphics/presentation-capable queue family initially, one frame in flight before concurrency. Add a separate-family implementation only as an explicit extension with ownership-transfer teaching. Required features, formats and queue support are selected by capability, not by taking the first device. [Khronos rendering overview](https://docs.vulkan.org/tutorial/latest/01_Overview.html).

Draft presentation-lifetime baseline: require a verified swapchain-maintenance implementation with presentation fences, initially the documented `VK_EXT_swapchain_maintenance1` route and its required dependencies/features. Unsupported hardware gets a capability report and may run offscreen exercises; it does not pass the windowed renderer gate. This explicit requirement avoids teaching that an ordinary submission fence or `vkDeviceWaitIdle` alone proves presentation resources can be destroyed. Present-wait semaphores are associated with acquired images rather than blindly recycled by frame index. [Khronos presentation-lifetime guidance](https://docs.vulkan.org/guide/latest/swapchain_semaphore_reuse.html).

The exact SDK, extension spelling/availability, dependencies, loader, shader compiler and validation-layer versions must be pinned and tested before the first executable lesson is released. A future compatible core/KHR route may replace the chosen extension after its semantics and supported machines are checked. This draft makes no claim that a tested Vulkan setup already exists in this repository.

SDL3 remains the platform layer for windows/events and surface creation, not the Vulkan renderer. The lesson obtains the instance extensions required by SDL instead of guessing platform names. [SDL Vulkan integration](https://wiki.libsdl.org/SDL3/CategoryVulkan).

## Chapter D1 — Ask the machine what it supports

| Lesson | Problem and files | Mechanism and vocabulary | Independent challenge and evidence |
|---|---|---|---|
| D01 — Is this machine a supported target? | Add a Vulkan toolchain/capability worksheet and a small probe target. | Driver, loader, SDK, API version, device support, extension and validation layer. Installed headers are not proof a running driver supports a feature. Distinguish instance requirements from device requirements. | Diagnose separate missing-tool, missing-loader and unsupported-feature scenarios. Record actual versions and device details. Unsupported configurations fail with a reason, not a blank window or a skipped test called passed. |
| D02 — Read an API structure in ordinary C++ | Type a tiny structure experiment before instance setup. | Handles, zero initialization and required named fields. Explain sType separately from pNext; neither is magic boilerplate. | Build two distinct request values and identify required fields with documentation hidden. |
| D02b — Combine flags deliberately | Add an isolated bit-mask experiment with printed integer and boolean results. | Bitwise OR versus logical OR; checking a required flag. | Select a different allowed combination and reject a logical-OR mutant. |
| D02c — Borrow an array for one call | Use an owned array and a small test API before Vulkan enumeration. | Pointer/count agreement, output parameters and duration of a borrow. | Handle empty/nonempty inputs, detect count disagreement and explain why an escaping local pointer is invalid without executing it. |
| D03 — Create an instance from queried requirements | Build vk/Instance through separate enumeration, selection, creation and destruction edits. | Instance, layer, extension and checked result; reuse the already-taught API-structure and pointer/count mechanisms. | Explain missing required versus unavailable optional capabilities, and clean up one successfully created instance. |
| D03b — Hear and classify diagnostics | Teach an ordinary C++ callback experiment before registering Vulkan validation output. | Function pointer, callback signature, severity and user-data lifetime. | Prove the real callback receives a controlled diagnostic, identify its rule, repair it and rerun; silence with validation disabled is not success. |
| D04 — Connect the window to presentation | Add `vk/Surface` using SDL's required extensions and surface operation. | Surface, platform integration, parent/child lifetime and ownership across APIs. A surface identifies a presentation destination; it is not the image being drawn. | Explain and test destruction ordering during partial setup failure. Verify the SDL event loop still responds while no rendered frame exists. |
| D05 — Select a usable device and queue | Add capability selection and a logical `vk/Device`. | Physical versus logical device, queue family, queue, feature query versus feature enable, limits and surface support. Pure selection logic operates on captured capability records for tests. | Reject a fast-looking device missing required features and select a supported one. Test no-supported-device behavior. State the single-family constraint clearly instead of assuming graphics implies presentation. |

Gate: obtain a meaningful capability report, explain every required feature and create/destroy the instance/surface/device without unaccounted resources. Device-selection tests may use fabricated capability records; at least one actual machine must validate the real path.

## Chapter D2 — Get one image safely onto the screen

| Lesson | Problem and files | Mechanism and vocabulary | Independent challenge and evidence |
|---|---|---|---|
| D06 — Give resources an ownership tree | Refactor the working setup into small noncopyable owners. | Parent handle, child resource, RAII, move and partial construction failure. Apply earlier C++ knowledge, but distinguish CPU object lifetime from outstanding GPU use. | Inject a failure after each successful creation and observe one release per owned resource. Borrowed handles are never independently destroyed. No catch-all cleanup list with unexplained ordering. |
| D07 — Choose swapchain properties | Add a pure chooser and `vk/Swapchain` creation. | Surface format, color space, extent, image count, usage, presentation mode and availability. Explain mandatory constraints versus preferences using reported capabilities. | Test clamping a requested size/count to supported bounds and choosing a fallback format/mode. Build against actual reported support; arbitrary hardcoded image counts must fail a selection test. |
| D08 — Images need views | Enumerate presentation images and create their views. | Image versus image view, subresource, aspect and borrowed image ownership. The swapchain owns its images; the application owns created views. | Build a resource ledger from real handles and explain which releases exist. Test a partial view-creation failure without destroying borrowed swapchain images. |
| D09 — Record commands before submitting | Add `vk/CommandPool` and a command-buffer lifecycle experiment. | Command pool, recording, executable, pending and reset states. Draw a state diagram with legal transitions. Begin with no GPU resource mutation so the lifecycle can be isolated. | Reject a simulated reset while pending in the CPU model, then observe the actual valid lifecycle under validation. The CPU model is an explanation aid, not a substitute for driver checks. |
| D10 — An image has a usage history | Add explicit image barriers around a clear/rendering operation. | Layout, pipeline stage, access, execution dependency and memory visibility. Trace old use → dependency → new use. Explain discarded prior contents separately from preserved contents. | Complete a transition table for first use and later reuse. Diagnose an intentionally missing dependency using validation where detected. Do not claim a layout name alone synchronizes access. |
| D11 — Know when submitted work finishes | Trace a submission fence using one frame in flight before reuse. | CPU waiting, GPU completion, signal/reset states and cancellation without submission. | Diagnose a reset that no future submission will signal; verify the real valid sequence with validation active. |
| D11b — Connect acquisition to GPU work | Extend the timeline with acquisition and binary semaphore dependencies. | Acquire result, wait, signal and which resource each dependency protects. | Classify safe command/acquire-resource reuse and reject a timeline that omits the acquisition dependency. |
| D11c — Retire presentation resources separately | Apply the verified presentation-maintenance path and per-image present-wait semaphore ownership. | Presentation completion versus submission completion, retirement evidence and parent/child lifetime. | Demonstrate why an ordinary submission fence is insufficient; verify actual presentation-fence retirement on the selected implementation before integrating the clear loop. |
| D12 — Clear, submit, present | Integrate a shader-free clear with dynamic rendering and synchronization2. | Rendering attachment, load/store operation, acquire result, submit and present result. Every API structure now answers a previously taught question. | Alternate colors while processing window events. Run a bounded sequence, collect validation output and observe actual frames. A skipped/minimized frame must not be counted as a presented one. |
| D13 — Resize is a resource transition | Recreate size-dependent resources and retire old presentation resources safely. | Out-of-date/suboptimal result, zero extent, suspended rendering, recreation and deferred retirement. Reset submission fences only when a submission will follow. | Resize repeatedly, minimize/restore and close during a resize. Verify no deadlock, stale image/view use or premature present-resource destruction. Explain which properties force a rebuild and which do not. |

Gate: the cleared window is already a robust small Vulkan application. No triangle work starts until the learner can trace image ownership and synchronization. The [Khronos recreation lesson](https://docs.vulkan.org/tutorial/latest/03_Drawing_a_triangle/04_Swap_chain_recreation.html) is a reference for the fence-reset failure case; the curriculum's explicit presentation-retirement policy is reviewed separately.

## Chapter D3 — Draw familiar geometry through an explicit pipeline

| Lesson | Problem and files | Mechanism and vocabulary | Independent challenge and evidence |
|---|---|---|---|
| D14 — A compiled shader has an interface | Compile the previously understood HLSL calculations for the Vulkan path and inspect their input/output/resource contract. | Shader module, entry point, stage interface and SPIR-V. Explain which SDL GPU conventions were library conventions and which are Vulkan requirements. | Repair a deliberate mismatch between shader outputs and inputs. The build must regenerate an edited shader and reject a missing entry point. Do not accept an opaque downloaded binary as the learner's shader. |
| D15 — State every pipeline choice | Add pipeline layout and graphics pipeline creation in small semantic stages. | Input assembly, vertex input, viewport/scissor, rasterization, multisampling, depth and color output. Revisit C's concepts without assuming Vulkan structure fields are self-explanatory. Dynamic rendering declares compatible attachment formats. | Change winding/culling and predict visibility before running. Explain static versus dynamic state and why forgetting to set enabled dynamic state is a bug. |
| D16 — Draw the first triangle | Use a tiny vertex-ID-based shader experiment before adding memory allocation. | Draw command, vertex count and shader-generated positions. This isolates pipeline/submission from uploaded data; it is explicitly temporary. | Draw a second arrangement by changing known shader data. Compare orientation/colors with C. Explain why this milestone does not yet demonstrate a working vertex-buffer upload path. |
| D17 — A buffer is not its allocation | Create a vertex buffer and inspect its memory requirements without drawing from it yet. | Buffer usage, size, memory requirement, alignment and binding. C++ container memory and Vulkan device memory are separate things. | Validate candidate allocation size/alignment against reported requirements. A printed requirement report is this lesson's observable result; do not execute an unbound-buffer draw. |
| D18 — Choose and bind memory | Add a small dedicated allocation owner for one resource. | Memory type bits, property flags, host-visible, coherent, device-local, mapping and binding. Explain permitted combinations from queries rather than treating labels as mutually exclusive. | Select a compatible memory type from several records; reject no-match. Write/read a mapped test value when supported and follow coherent/noncoherent rules. Explain who unmaps and frees, and in what order. |
| D19 — Upload data and make it visible | Add staging, a copy command and the dependency needed before vertex consumption. | Transfer source/destination, host writes, flush ranges, GPU copy and access visibility. Work through a byte-range example including required alignment. | Change uploaded vertices and prove the new image uses them. Detect a wrong copy size with bounds checks and validation. A fence wait answers completion, not every visibility/layout question by itself. |
| D20 — Indexed meshes, familiar math | Bring in `Mesh`, index buffers and the known cube/board data. | Index binding, draw-indexed parameters and byte offsets. Reuse the math and mesh contracts from C; type only the Vulkan adapter and any explained interface changes. | Draw a new mesh with validated indices and compare against the SDL GPU scene. Diagnose an incorrect offset without changing game logic or replacing the mesh with a magic sample. |

## Chapter D4 — Bind data and render the scene

| Lesson | Problem and files | Mechanism and vocabulary | Independent challenge and evidence |
|---|---|---|---|
| D21 — Describe what a shader may access | Build a descriptor-set layout and connect it to the pipeline layout. | Descriptor, binding, descriptor type, shader stage visibility and set layout. Contrast a description of a resource slot with the resource itself. Keep the first case to one uniform buffer. | Map a shader declaration to the correct set/binding contract. A descriptor-layout mismatch must be diagnosed before adding textures. |
| D22 — Allocate, write and bind descriptors | Add pool, set allocation and resource writes for the transform. | Descriptor pool, set, update, bind and lifetime. Descriptor data does not own the buffer; it refers to it. One frame in flight makes the first update-safe point explicit. | Move two objects using taught uniform data. Explain when a buffer or descriptor may be modified. Test numerical packing and run real validation; avoid updating resources still in use. |
| D23 — A sampled image crosses several stages | Add a texture image, allocation, upload, view, sampler and descriptor in separate edits. | Image usage, copy regions, subresource ranges and sampled-image layout. Relate each to C's already understood sampling operation. | Load the known pattern and repair a wrong row offset or image origin. Exercise missing/bad assets and staged failure cleanup. Compare chosen sample locations with the reference scene. |
| D24 — Depth is another owned image | Create a supported depth image and attach it to rendering; add the known normals/light. | Depth format capability, aspect mask, attachment state and size-dependent resource lifetime. Resize must recreate matching depth resources. | Reverse opaque draw order and preserve visible surfaces. Stress resize and explain why the old depth image cannot be freed while referenced by pending work. |
| D25 — Small frequent data and overlays | Introduce push constants with one small parameter, then restore the game overlay. | Push-constant range, stage flags, implementation limits and command-recorded data. Compare to uniform-buffer data; neither is a universal replacement. | Change a highlight per draw and preserve layout compatibility. Test a boundary against queried limits and inspect correct overlay blending. Defer descriptor indexing and bindless rendering. |

Gate: render the same model through the SDL GPU and Vulkan backends with controlled camera and inputs. Compare scene intent, numerical transforms and selected visual features; do not require bit-identical screenshots across drivers.

## Chapter D5 — Concurrency, diagnosis and a finished milestone

| Lesson | Problem and files | Mechanism and vocabulary | Independent challenge and evidence |
|---|---|---|---|
| D26 — More than one frame can be pending | Expand from one frame to a small frame-context ring after measuring idle time. | Frames in flight, frame index versus image index, per-frame command/uniform resources and safe reuse. Keep present-wait resources keyed by the appropriate presentation lifecycle. | Trace a swapchain image count different from the frame count. Reproduce and fix the wrong-index mutant. Validation, resize and shutdown must still pass under repeated runs. |
| D27 — Reclaim only after the right completion | Add explicit resource retirement for pending uploads, replaced textures and swapchain recreation. | Deferred destruction, retirement condition and completion token. Presentation and submission have different completion proofs. A destructor can delegate safe retirement instead of blindly freeing a live GPU object. | Replace a texture while frames are pending. Show when its old allocation becomes reclaimable. Exercise shutdown after partial setup and after submitted/presented work. |
| D28 — Diagnose a broken frame | Build a fault laboratory using controlled bad configuration/data and a GPU capture tool supported on the target. | Validation message, rule identifier, capture, draw inspection and minimal reproduction. Do not encourage arbitrary undefined behavior on the learner's driver. | Diagnose a blank frame caused by culling, viewport or wrong resource binding. State the evidence before the fix. A clean validation log is necessary but not proof the image is correct. |
| D29 — Measure one change honestly | Add a measured experiment such as fewer uploads or batched draws. | GPU timestamps, CPU timing, synchronization overhead, warm-up and profiling perturbation. Check timing feature availability and valid timestamp scope. | Compare before/after with a fixed scene and protocol. Explain a case where CPU submit time improves but GPU time does not. Do not replace the understandable allocator with a complex memory system without measured need. |
| D30 — Plug the backend into the game | Complete `VulkanRenderer` behind the minimal interface proven in C. | Adapter, backend boundary and composition root. Keep selection/configuration outside rules and ML. | Replay one match through terminal, SDL2D, SDL GPU and Vulkan applications, comparing game states. Add one independent visual feature and explain which shared files it did and did not need to change. |
| D31 — Release with stated limits | Write the device requirements, setup, shader build, controls, error-recovery guide and validation report. | Compatibility contract, reproducibility and release evidence. A missing optional feature must not become an undocumented crash path. | Build on a clean supported environment, run tests and actual presentation, resize/minimize/restore, then shut down without lifetime errors. Explain every major resource and synchronization edge without reading the setup code. |

## Proposed implementation structure

The source files appear as their responsibilities are taught, never as an initial wall of empty classes.

```text
dice-lab/
  include/vk/         Instance.hpp, Surface.hpp, Device.hpp, Swapchain.hpp
                      CommandPool.hpp, Buffer.hpp, Image.hpp, Pipeline.hpp
                      FrameContext.hpp, VulkanRenderer.hpp
  src/vk/             matching implementations and pure capability selectors
  apps/               vulkan_probe.cpp, vulkan_game.cpp
  shaders/vulkan/     source only where a backend-specific contract requires it
  tests/              capabilities_tests.cpp, memory_selection_tests.cpp
                      resource_ledger_tests.cpp, renderer_contract_tests.cpp
```

Selection functions remain functions. Handles that need coordinated ownership get small classes. Do not force all GPU allocations into inheritance hierarchies. `FrameContext` owns reusable submission resources; `Swapchain` owns or tracks presentation-dependent resources under the taught lifetime policy. `VulkanRenderer` coordinates those objects but does not absorb all their code into one enormous class.

## Core scope versus later extensions

The core ends with a correct small renderer and a playable game, not a production engine. Multiple queue families, asynchronous compute, timeline-semaphore scheduling, mip generation, multithreaded command recording, allocation submanagement, advanced lighting, ray tracing and a model importer are subsequent projects. Each needs its own prerequisite and validation plan. Naming them here does not make them assumed background knowledge.

For Vulkan Memory Allocator or Vulkan-Hpp, a later comparison can replace a learner-built responsibility after its contract and limitations are understood. Using a library is a legitimate engineering decision; leaving its ownership behavior unexplained is not.

## Release evidence required

Run CPU selection/math tests, compiler and shader builds, wrong-answer tests, validation-enabled driver runs and actual presentation checks. The hardware report must identify API/features/extensions, driver, OS and selected formats. Add bounded smoke modes but keep close/resize/minimize and visual correctness checks distinct from them. Record unsupported hardware and skipped tools plainly.

The final explanation gate asks the learner to trace: a byte from CPU data to device memory; a vertex to a fragment; one acquire/submit/present cycle; and a resource from creation to safe retirement. If any part is still described as “boilerplate,” revisit the corresponding chapter before calling the path complete.
