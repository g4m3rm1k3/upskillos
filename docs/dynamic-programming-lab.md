# Dynamic Programming Lab

The lab at `#/lab/dynamic-programming` (`src/labs/dynamic-programming/`). Read this first when resuming. **Update this doc only when the context is large enough that a fresh session (which must re-read the code) is cheaper than carrying on.** Finishing a family, a plan item or a lab is not a reason to update it, to stop, or to ask whether to continue: go straight on to the next piece. The owner has had to repeat this every session. The bar it is built to is [lab-quality-standard.md](lab-quality-standard.md).

The owner's brief (2026-10-17): DP should be **better than every other lab**, really teach and challenge, and cover every topic. It must be **very visual and hands-on**, because DP teaches how to think and break problems down: animations, step through, "click this, watch". When solving, the learner wants to **run and print**, not only check, and to **open the harder problems in CodeLens**.

## What is there

- **Curriculum** (`curriculum.js`): 253 concepts in 6 levels, Foundations to Specialist, each with a stable id, title and scope. Every concept has a lesson (`lessons/`), so none are "coming soon".
- **Design it yourself** (`DesignIt.jsx`, content in `lessons/designs.js` and one `lessons/design-<family>.js` per family) on all 87 Core and Structured lessons (one file per family, `lessons/design-<family>.js`): stage 00, before any explanation. The learner solves a small case by hand (common wrong answers get a named diagnosis), then makes six decisions: what a cell means, the last choice, the recurrence, base cases, fill order, where the answer is. Every option has a reason, and the wrong ones are real mistakes. The right option is shown in a rotating position (`displayOrder`), because authors tend to write it first. Each right choice joins a "Your design so far" card. It ends with one cell of the live table computed by hand, diagnosed with `diagnose()`. Finishing it is saved, along with the wrong-pick count and whether an answer was shown.
- **A lesson** (`Lesson.jsx`) has three stages after that: Understand (sections, procedure, proof, complexity, pitfall), Walk through, and Solve a problem (a coding challenge) or Check understanding (one typed answer).
- **Live table** (`TableTrace.jsx`, data in `tables.js`) on 86 lessons, in the Walk through stage:
  - *Watch it fill*: play, pause, step, scrub, speed, arrow keys. The cell being written glows; arrows come from the cells it reads; the arithmetic is written out; base cases are listed first; the answer cell is marked.
  - *You fill it*: type each cell before it is revealed. Wrong answers get a diagnosis (copied one input, added instead of max/min, off by one). "Show the rule" after one miss, "Reveal" after two. Hard mode hides which cells are read. A clean run is saved ("✓ Filled by you").
  - *Fill order*: click cells in any order; a cell fills only when everything it reads is filled, otherwise the missing cells flash red with arrows. Ends by naming it: a topological order.
  - *Walk back* (on 43 lessons, `walks.js`): from the answer back to a base case, which choice made each cell, with ties named. The choices read forwards are the solution (the subsequence, the items, the path). "Let me choose" makes the learner click the cell each value came from; a wrong cell gets told why it did not win. On 8 interval lessons the solution is a tree: a split leaves two pieces, which wait outlined and are explained one after the other, and the solution is read off as it grows, with "…" for pieces not reached (the bracketing, the BST, the burst order, the cut order, the triangles, a true bracketing, the extreme bracketing).
  - *Change the input*: every trace takes the learner's own input (lists, strings, grids, triangles, numbers), with limits and plain-language errors, "🎲 Surprise me" and "Lesson example".
- **Call tree** (`CallTree.jsx`, data in `trees.js`) on 15 lessons (11 recurrences; the recursion and memoization lessons use Fibonacci): the plain recursion drawn as a tree and played call by call, with the call stack highlighted. Repeated questions share a colour. The learner predicts the number of calls first (the counts stay hidden until then). The memo switch collapses the tree. "From tree to table" lists states in the order they return, which is a table order.
- **Coding challenges** (69; `lessons/challenges.js`, `core-challenges.js`) in Python (Pyodide) or JavaScript, run in a worker that can be stopped (`runtime/`):
  - **▶ Run**: runs the code as written, shows everything it prints / `console.log`s, and what `solve(...)` returns for the input in the Run box (examples one click away). Not graded. Errors name the learner's line.
  - **✓ Run & check**: the hidden cases. A failing case has "Put this input in the Run box".
  - **🔍 Open in CodeLens** on challenges past the Foundations level: the learner's code plus one `solve(...)` call on the Run box input, stepped line by line in CodeLens. The lab window minimises while CodeLens is open; "Back to the DP lab" reopens it on the same lesson and stage.
  - Ctrl+Enter runs, Ctrl+Shift+Enter checks. Drafts, hints and passes are saved per lesson and language (`progress.js`).
  - **The reference solution, explained** (`Explained.jsx`, content in `lessons/explained.js`) on all 40 Core lessons: after the learner's first Run & check (or a pass), the lesson's solution in their language, with a note under each line that matters and a table of every maths symbol beside the code that holds it.
- **Bug hunts** (`Hunt.jsx`, `hunt.js`, content in `lessons/bug-hunts.js`) on 12 Core lessons: stage "04 · Bug hunt". The explained reference code with one classic bug swapped in: run it on the input that shows it, click the wrong line (a right line says why it is right; clues, then "Show me the line"), read why it breaks the method, fix it, pass Run & check. Saved as `hunt` in the synced record, ✓ on the stage when fixed.
- **Recursion lesson** (`RecursionLesson.jsx`): a reversible call-stack trace of a sum, with a checked prediction.

## How to add to it

- **A design** (plan item 1): add an entry to a `lessons/design-*.js` file and spread it into `DESIGNS` in `lessons/designs.js` (the format is described at the top of that file). `designs.test.js` checks the six kinds in order, one right option with a reason for every option, the right option not always in the same place, the hand-solved answer and the misconceptions against the brute-force oracle, and the apply cell against the live trace. Put every number quoted in an option's reason into its `CLAIMS` list.

- **A live table**: add a function to `TRACES` in `tables.js` taking one input object with the lesson's example as defaults. Use `table()` / `line()`; every `set` lists the cells it read and the arithmetic. Add its fields to `INPUTS`. `tables.test.js` then checks it fills in dependency order and agrees with the lesson's reference solution (or an `ORACLE` in the test, written without DP) on the example and on 25 random inputs that went through the real input parser.
- **A walk back**: add an entry to `WALKS` in `walks.js` (`back(trace, at)` returns every option that gives the cell's value, with `from`, `says`, `gain` and `adds`) and a check of the solution to `VALID` in `walks.test.js`. The tab appears by itself. For a tree (`tree: true`), build each option with `split(t, cells, gain, says, make)`: base cells are folded into the gain, `make(render)` writes the piece, and `leaf(trace, cell)` writes a base cell. `VALID` must rebuild the solution's objective from the spelled result (multiply the bracketing out, replay the order), not trust the walk.
- **An explained solution**: add an entry to `EXPLAINED` in `lessons/explained.js`: readable code in both languages, `notes` as `[pythonText, javascriptText, note]` (each attaches to the first line, at or after the previous note's, containing that text), and `math` rows `[maths, python, javascript, meaning]`. `explained.test.js` runs both versions against the challenge (real Python too) and checks every note and every code name is in the code. The scratch scripts that wrote the batches were plain Python appending to the file; any way works.
- **A check** ("Check yourself"): add a list to a `lessons/checks-<family>.js` file and spread it into `CHECKS` in `lessons/checks.js` (format at the top of that file). Each check has `know`, then a choice (one right option, a reason on every option) or a number (`args` for the oracle, `misconceptions`, `explain`; `oracle` for an answer that is not the challenge's, defined in `EXTRA` in `checks.test.js`). Put every number quoted in the text into `CLAIMS` in `checks.test.js`. Print the oracles' answers before typing any number.
- **A bug hunt**: add an entry to `HUNTS` in `lessons/bug-hunts.js` for a lesson that is in `EXPLAINED`: one `swap` per language (the right lines, the buggy lines), a symptom (args, the oracle's answer, what the buggy code returns), `know`, `why`, `fix`, three clues and decoy notes. Find the symptom by searching small random inputs against the oracle, never by guessing. `bug-hunts.test.js` checks the rest, including that the buggy code fails the lesson's own challenge.
- **A call tree**: add a spec to `TREES` in `trees.js` (`params`, `root`, `label`, `children`, `combine`) and map lessons to it in `TREE_FOR`. Add the matching table input to `AS_TABLE` in `trees.test.js`, which checks the tree's answer against the table for every parameter value.
- **A challenge**: see `challenges.js`; expected values come from brute-force oracles (`core-oracles.js`), never from the DP solution being taught.
- Use `trace.css` for the visual components' styles; `style.css` holds the shell.

## Progress and sync

All lesson progress (drafts, passes, quiz, design) is in one localStorage key, `oc-dp-lab` (`progress.js`), which is in `SYNC_KEYS` (`src/context/AuthContext.jsx`). It reaches the learner's account when they are signed in, and a new solve is pushed at once with `pushNow`. Two devices merge with `mergeDpLab` (`src/context/progressMigration.ts`): a pass on either side wins. The old per-lesson keys (`upskillos.dp.v1.<id>`) move into it the first time they are read. A solve shows as a ✓ on the lesson in the sidebar, a ✓ Solved badge on the lesson, ✓ n/m counts on levels and groups, and the header bar. Still local only: the trace's "Filled by you" marks (`upskillos.dp-lab.trace.<id>`).

## Pitfalls found so far

- **Shell heredocs break** when the text contains apostrophes or backticks: the Bash tool reports "unexpected EOF" and writes nothing. Write files with the Write tool, or a Python script with no backticks in it.
- **Component tests need** `// @vitest-environment happy-dom` on line 1, or they fail with "document is not defined".
- **CodeLens opens beneath the lab's desktop window** unless the window is minimised first (`useDesktop()?.minimizeWindow('dynamic-programming')`). Use `window.location.hash`, not `useNavigate`, because the lab's tests render it without a router.
- **The browser check meets a "What's new" popup** after a reload; it clicks "Got it". After resizing the viewport, reload, or the desktop keeps the window at its old size.
- **The grid-paths challenge allows diagonal moves**, but the lesson and table don't, so the table is checked against its own right/down oracle in `tables.test.js`.
- **The 14 "content problems"** reported by `npm run catalog:check` predate this lab; don't chase them here.
- **Element screenshots in the narrow window** show page content from behind the lab below the window's visible area ("Open Lesson Engine"). It is the screenshot capturing the element's whole box, not a layout bug; check that the page does not scroll sideways instead.
- **The browser check opens lessons by an anchored title match** (`openConcept`): a plain text match opened "Unbounded knapsack" for "Bounded knapsack".
- **The browser check waits for a decision's reason** before clicking "Next decision"; clicking while it re-renders failed once (a flake).
- **Shell heredocs with apostrophes** still break (twice this session): write a Python file with the Write tool and run that.
- **The browser check waits for the lesson heading** after opening a lesson; without it, answers went into the previous lesson's panel (a race, seen once).
- **Type numbers only after computing them.** Writing a design's answers by hand got three of 16 wrong. Print each oracle's answer next to the typed one before running the tests.
- **The lab's base button style** (`.dp-lab button`) has no border or padding. A new plain button needs a class (`dp-di-secondary`) or it shows as bare text.
- **A hunt's symptom must be computed, not guessed.** Two of the first twelve were guessed and did not show the bug. Search small random inputs against the oracle (a scratch script: buggy code against `ORACLES[id]`) and take the smallest. The memo-key bug passed every subset-sum challenge case, so that challenge got the symptom as a new case: a hunt's bug must fail its lesson's own challenge.
- **`.dp-lab button` outranks a plain class rule in `style.css`**: `.dp-btn-hint` showed as bare text on every challenge. Style lab buttons with `.dp-lab .name` in `trace.css`.
- **A claim in `checks.test.js` runs its oracle**, and the Structured oracles enumerate: a distinct-subsequences claim on 30 letters listed 2³⁰ subsequences and crashed the test worker. Keep claims to inputs of about 12 letters or values, and check a large number through a cheap oracle (`binomial`) instead.
- **Recipe that worked for every family (keep it):** write the oracles (enumeration, never DP) and solutions; fuzz the JS solution against the oracle on 300 random inputs with `Math.random` (an LCG's low bits repeat and starved four searches once); pick cases whose large one has a closed form (binomial, Fibonacci, 9¹⁵, …) so it is checked without the oracle; search bug symptoms with the buggy explained code against the oracle; a bug that passes its own challenge gets its symptom added as a challenge case (needed for dag-paths, subset-cover, kmp-dp, pareto-frontiers, bounded-binary).
- **Proofread every "wrong" option**: about one in eight first drafts was an option that also works (a slower but correct method, an equivalent state). Replace it with one that fails.
- **Test length limits** (know > 40, why > 25/30, explain/feedback > 20, hunt fix > 40, know > 80, maths table ≥ 2 rows, ask > 15): scan a new file for short fields with a one-line node script before running the tests; the tests stop at the first.
- **The number box parses numbers**: a table cell or design answer that is a string can never be typed. Use a number cell, or ask a numeric question through another oracle (`oracle: 'kmp-dp'`, `PICK`).
- **A hunt's symptom must not crash** either language (an empty deque gives `null` in JS and an exception in Python, and the test compares the printed value).
- **Hunt text shows Python strings in single quotes** (`show` in `hunt.js`), to match Python's `repr` in Run.
- **Draft the next family in the scratchpad while a browser check runs** (lab files must not change during one): oracles, solutions, challenges, explained code and hunts as scratch modules, fuzzed there against each other in both languages, then moved into the lab by a script. Nothing waits on the browser.
- **A list answer** (fft-ntt, sos, mobius, subset-convolution, walsh-hadamard): the trace returns `check: want => want[i]` for its answer cell; a design's try-first reads the list through `PICK` in `designs.test.js` (the last entry); a check picks one entry with `part`.
- **A trace whose input fields are not the challenge's args** returns `input` as well as `args` (bostan-mori takes r and passes Q = 1 − r₁x − …), or the default-input round trip fails.
- **JavaScript products modulo p ≈ 10⁹ are not exact.** The references use `mul = (a, b) => ((a * (b >>> 16)) % M * 65536 + a * (b & 65535)) % M` (exact for a, b < 2³⁰), and BigInt where values pass 2⁵³ (cht-numeric). Keep the hull challenges' constraints small enough that their cross-products stay below 2⁵³, and say so in the constraint.
- **Slower-but-correct "wrong" options slip past every test.** Eight were found in finished families: "one 0/1 item per copy", "the full table", "multiply by x, n times", "the k × k matrix power". For every wrong option ask: would this give a wrong answer? If it only costs more, replace it with one that fails. A replacement can still be correct ("W(i) and the largest W so far" keeps W(i)): reread it.
- **Redundant checks hide a hunt's bug.** In profile-obstacles, the blocked cell rejects a covered mask *and* placement never lays a domino on a block; removing either alone changes no answer (the search found no symptom). Pick a bug no other line catches. Likewise "the sum over all final masks" equals the answer when edge checks stop pieces hanging off the board: such a "wrong" design option is right.
- **A hunt whose bug grows the state space** (plug-dp with an uncleared plug) timed out on the large case in both languages. Choose bugs that keep states bounded.
- **Component tests used `plug-dp` as a quiz-only lesson**; it now has a challenge and design. `progress.test.jsx` uses `matrix-chain` (Structured keeps a quiz); `index.test.jsx` uses `proof-checklist`, the last Specialist lesson to be built: when research-tools is done, that test needs another walkthrough-only lesson (or rewriting).
- **"Fill order" is a step's heading**: put fill-order questions there, not "why rename labels" (moved to checks).
- **Other sessions share this working tree** (see the owner's parallel-sessions note): commit only DP lab files and this doc.
- **Drafting outside the lab worked for four groups in a row**: in `local/dp-specialist-drafts/` (untracked), per group a `<group>-code.js`, `<group>-oracles.js`, `fuzz-<group>.mjs` (exports `GEN`), `<group>-cases.mjs` (case values with closed-form checks and Python timings), `swaps-<group>.mjs` and `symptoms-<group>.mjs`; then a Python script in the scratchpad moves them into the lab (challenges, oracles, explained, hunts, traces, inputs) and `verify.mjs <ids>` re-checks every case in both languages.
- **Helper names clash in `specialist-oracles.js`**: each group's oracles bring their own fraction helpers; rename them per group (`gcdP`, `Qc`, …) and check for an existing `const` before appending.
- **Heredocs turn `\b` into a backspace** (and drop other backslashes): a regex written in a Bash heredoc silently matched nothing and a duplicate `const` reached the lab. Write Python files with the Write tool.
- **A hunt bug must not grow the state space** (again): pomdp's unnormalised belief made every belief new, so the memo never hit and the 30-turn case ran for minutes in the hunt tests. Its bug is now "repair doesn't change the belief".
