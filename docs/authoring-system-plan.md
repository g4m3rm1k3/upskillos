# Authoring System Plan

Status: design and implementation backlog

Last reviewed: 2026-09-26

## Goal

The project owner or a contributor should be able to learn through any course, lab, or game and improve it at the point where a problem is found. Author mode should answer four questions without requiring prior knowledge of the repository:

1. What resource am I viewing?
2. Which source files produce it?
3. Which parts can be edited safely here?
4. Which checks must pass before the change is saved or contributed?

The system should preserve specialized experiences such as Machine Learning Lab. A shared authoring contract should describe how to edit a resource; it should not force every resource to use the same runtime renderer.

## What works today

| Surface | Current behavior | Practical limit |
|---|---|---|
| Course lesson | Every standard lesson page links to `/lesson-builder/:chapterId/:lessonSlug`. The builder loads the lesson object and raw source, converts recognized fields to blocks, previews the result, checks LaTeX, and can show a diff, save locally, copy source, or create a pull request. | The repository contains several historical lesson shapes. Unknown fields are preserved where possible, but an unrecognized shape can still be unsafe to round-trip. |
| SVG displayed through `SVGImage` | In local development, hovering the diagram exposes an editor with source, visual editing, live preview, save, and pull-request actions. | It works only when the rendered URL can be mapped back to a source SVG under the repository. It does not cover inline React SVG, Canvas, Three.js, or figures generated by code. |
| SVG Gallery | Lists editable SVG assets and opens the same SVG editor. | It currently discovers only Calculus and Geometry diagram folders rather than all repository SVG assets. |
| Viz Builder | Configures registered visualizations, previews them, and can insert a visualization configuration into a standard course lesson before using the Lesson Builder export flow. | Its target picker only knows standard course lessons. It cannot target a custom lab lesson or edit an arbitrary React visualization implementation. |
| Local saving | Vite's development server exposes a filesystem API used for reads, diffs, and writes. | This exists only while running the local development server. The path-boundary and allowed-write-root checks need hardening before this becomes the foundation of a universal author mode. |
| Desktop contributor support | Contributor-mode components and clone support exist. | `ContributorGate` is not mounted on the builder routes, and the current `available` flag only reflects the Vite development filesystem API. The actual desktop editing path needs an end-to-end test. |

## Why Machine Learning Lab is different

Machine Learning Lab is one catalog lab containing 61 curriculum labs. It does not use `courseLoader` or the standard course lesson object. Its content is deliberately split across several responsibilities:

| Source | Responsibility |
|---|---|
| `src/labs/ml-lab/labs/index.js` | Registers all 61 curriculum labs |
| each lab's `index.js` | Title, question, introduction, lessons, sources, Python exercise, playground, figures, ladders, math links, and scope |
| `lessons.js` | Lesson prose, objectives, prerequisites, formulas, notebooks, experiments, and checkpoints |
| `blocks.js` | Order of prose, figures, cells, predictions, derivations, and practice ladders |
| `python.js` | Starter code, checks, hints, solution, packages, and runtime limits |
| `figures.jsx` | Lab-specific interactive diagrams |
| `Playground.jsx` | The main experiment for a lab |
| `ladder.js` | Retrieval-practice logic |

This is already an implicit lab specification, but it is enforced by convention and tests rather than a versioned authoring contract. The standard Lesson Builder cannot infer which of these files should change from one editing action.

## Target architecture

### Author mode

Add one explicit Author mode that is visible only when a writable local checkout is available. On any authorable resource it should provide:

- **Edit content** for prose, objectives, prerequisites, examples, and assessments;
- **Edit visual** for an SVG asset or a registered declarative visualization;
- **Edit source** for custom React, Canvas, Three.js, or runtime code;
- **Review resource** for recording correctness, beginner usability, accessibility, and responsive status;
- **View files** to explain which repository files produce the current screen;
- **Preview changes**, **run checks**, and **save** as one guided flow.

The default learner interface should remain uncluttered when Author mode is off.

### Versioned authoring contract

Introduce an executable `AuthorableResource` contract with adapters. Conceptually, each resource supplies:

```text
version
resource id and kind
display route
source files
editable regions and their editor type
visual assets and their editor type
progress identifiers
validation commands
parse, preview, and serialize behavior
```

Editor types should include structured lesson fields, Markdown, JavaScript object data, SVG asset, visualization configuration, Python exercise, and source code. The contract should use runtime validation and TypeScript types generated from or tested against the same definition.

### Adapters instead of a mass rewrite

Build adapters around current formats:

1. **Standard course lesson adapter** — wraps the existing `lessonToState` and serializer pipeline.
2. **Machine Learning Lab adapter** — maps the existing module, lesson, block, Python, figure, playground, and ladder files into authoring regions.
3. **Markdown/narrative lab adapter** — supports labs whose content is already data or Markdown.
4. **Custom lab adapter** — exposes declared source files and safe editors without pretending arbitrary React is a drag-and-drop lesson.
5. **Game adapter** — exposes instructions, learning objectives, question banks, tuning data, visual assets, and implementation source where each game declares them.

An adapter may mark a region as source-only. That is safer than silently rewriting code the structured editor does not understand.

### Visual asset registry

Every editable visual should declare one of these source types:

- **SVG asset:** open in the SVG source and visual editor;
- **visualization configuration:** open in Viz Builder;
- **React SVG component:** open its source with a live component preview;
- **Canvas, Three.js, or other code visualization:** open source plus its existing runtime preview;
- **generated or remote asset:** display its origin and explain why it cannot be edited directly.

Replace the hard-coded Calculus/Geometry SVG Gallery globs with a generated asset registry. Course lessons, custom labs, and games can then use the same asset picker and editor.

## Machine Learning Lab first adapter

ML Lab is a good first custom-lab adapter because its structure is broad but consistent and extensively tested.

The first version should support:

- editing lesson title, skill, prerequisite, paragraphs, section labels, experiment, scope, and sources;
- arranging the existing block sequence without losing unknown block data;
- editing notebook cells, Python starter code, hints, checks, solution, and explanatory text;
- previewing the current lesson, figure, and playground in context;
- opening `figures.jsx`, `Playground.jsx`, and `ladder.js` in a source editor when no structured editor applies;
- running the affected lab's engine, lesson-flow, notebook, and Python verification checks before saving;
- showing a multi-file diff because one conceptual edit may touch several files.

Do not start by converting ML Lab into the standard course schema. Its notebook isolation, practice ladders, lesson-aware figures, code checks, and progress model would be easy to lose in that conversion.

## Learn-and-improve workflow

Author mode should support the owner's intended workflow:

1. Open a lesson or lab normally and complete it as a learner.
2. Turn on Author mode without losing the current location or work.
3. Record a review note against the exact lesson, visual, exercise, or interaction.
4. Open the appropriate structured editor or source editor in context.
5. Preview the change in the same learner view.
6. Run the checks selected by the resource adapter.
7. Review the source diff and save to the local checkout.
8. Mark individual review dimensions as checked; do not mark the whole resource reviewed merely because it was opened.

Review state should feed the planned generated content-health report. Store review evidence separately from runtime course metadata so a review date or reviewer name does not affect the learner bundle.

## Implementation order

### A0 — Make editing safe

- [ ] Restrict development filesystem reads and writes to explicit allowed roots using resolved path-relative boundary checks.
- [ ] Mount and test the contributor gate or replace it with one reliable capability check shared by every editor.
- [ ] Require a successful parse/serialize round-trip before structured editing is allowed.
- [ ] Show multi-file diffs and affected checks before saving.
- [ ] Preserve local changes and surface Git state; never imply that saving locally also commits or publishes.

### A1 — Complete course authoring

- [ ] Inventory every current course lesson shape and report which shapes are fully editable, partially editable, or source-only.
- [ ] Generate the SVG asset registry across all courses rather than only Calculus and Geometry.
- [ ] Add an Author mode entry point and consistent edit controls for lesson content and visuals.
- [ ] Run lesson schema, LaTeX, embedded-code, challenge, and focused render checks from the save flow.
- [ ] Add tests proving edits preserve unknown fields and imported assets.

### A2 — Define lab authoring and support ML Lab

- [ ] Implement the versioned `AuthorableResource` contract and adapter registry.
- [ ] Document the minimum catalog metadata separately from optional authoring capabilities.
- [ ] Implement the ML Lab adapter without changing its learner-facing renderer.
- [ ] Add multi-file editing and validation for ML prose, blocks, notebooks, Python exercises, figures, and playground source.
- [ ] Record review status for each of the 61 ML curriculum labs and their lessons.

### A3 — Extend coverage

- [ ] Classify every remaining lab by the nearest adapter and declare source-only regions explicitly.
- [ ] Add the game adapter and declare the content, assets, question banks, tuning data, and source for every game.
- [ ] Connect the authoring registry to the generated content-health report so missing adapters and unreviewed resources are visible.
- [ ] Add contributor lessons that teach the same in-app workflow and the underlying files it changes.

## Completion criteria

The authoring system is complete when:

- every catalog course, lab, and game can identify its source files and applicable checks;
- every standard course lesson can be edited safely or clearly marked source-only;
- every repository SVG asset is discoverable and editable when running locally;
- ML Lab can edit and preview its own native content model without conversion to the course schema;
- custom code visuals expose source and live preview even when no visual editor exists;
- saving presents an accurate diff, runs relevant checks, and writes only inside approved repository roots;
- review status distinguishes structural validation, subject correctness, beginner usability, accessibility, and responsive testing.
