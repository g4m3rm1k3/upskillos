Outcome: reproduce an asynchronous race with controlled promises instead of hoping for a slow network. A race occurs when output depends on which operation finishes first. Correct behavior depends on the latest user intent, not the most recent network completion.

### The story so far

The previous lesson used two protections: cancellation and request identity. This lesson turns their purpose into a reproducible experiment. A timing bug is easier to understand when you choose the completion order instead of repeatedly hoping the network behaves badly.

We are testing one invariant: once a newer query owns the screen, an older query cannot alter its result or error state.

## Walk the timeline

### Put intent order and completion order side by side

| Moment | User intent | Completed response | Allowed display change |
|---|---|---|---|
| 1 | Search A | None | Show loading A. |
| 2 | Search B | None | Show loading B; A is obsolete. |
| 3 | Still B | B succeeds | Show B’s result. |
| 4 | Still B | A succeeds | None; ignore A. |

The final row is the trap. “Last response wins” feels plausible because it uses recent activity, but it confuses two clocks. The most recent response may answer an older question.

### How a controlled promise helps

`new Promise(resolve => ...)` gives the test a function that can fulfill the promise later. The fake fetch stores those resolve functions in an array. Calling the second one before the first creates the exact sequence above. The fixture deliberately ignores abort so it can test the identity guard independently.

This is like holding two envelopes and choosing which to open first. The envelope analogy explains ordering, not JavaScript’s full scheduling rules. Promise continuations resume through the microtask queue; the test yields time for those continuations before observing the DOM.

**Rule of thumb:** make nondeterministic bugs deterministic in the smallest environment that still contains the failure. Controlled requests are better for this contract than repeatedly throttling a live API and hoping A happens to be slower.
