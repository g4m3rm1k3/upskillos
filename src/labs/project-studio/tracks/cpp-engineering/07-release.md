A release is a promise: *this* version, built *this* way, does *these* things. It needs a version number that the program itself knows, a way to install it, files people can download, and a mark in the history so the exact source can be found again in five years.

| Piece | Tool |
|---|---|
| one version number, in one place | `project(VERSION)` |
| the program knows its version | `configure_file`: a generated header |
| what goes where on install | `install()` rules |
| downloadable archives | CPack |
| the release's source, forever | a Git **tag** |

## Step 1 — A version, in one place

**This step: create `cmake/version.h.in`, a template for a header that CMake will fill in.**

interp is about to be **1.0.0**. Version numbers usually follow **semantic versioning**, `MAJOR.MINOR.PATCH`:

| Bump | When | Promise to users |
|---|---|---|
| PATCH: 1.0.0 → 1.0.1 | bug fixes only | upgrade without fear |
| MINOR: 1.0.1 → 1.1.0 | new features, nothing removed | old scripts still work |
| MAJOR: 1.1.0 → 2.0.0 | something incompatible | read the release notes first |

The number must live in **one** place, or the copies drift apart: the program says 1.0.0 while the archive says 1.0.1. That place is `project()` in `CMakeLists.txt`, and the code gets it from a generated header:

```cpp
#pragma once

namespace interp {

inline constexpr const char* version = "@PROJECT_VERSION@";

} // namespace interp
```

When CMake processes the template, `@PROJECT_VERSION@` becomes `1.0.0`. `inline constexpr` makes it a compile-time constant that can live in a header included by many files, with one definition for the whole program.

```cpp file=cmake/version.h.in
// Generated by CMake from cmake/version.h.in: edit that file, not this.
#pragma once

namespace interp {

inline constexpr const char* version = "@PROJECT_VERSION@";

} // namespace interp
```

```check
contains cmake/version.h.in "@PROJECT_VERSION@"
contains cmake/version.h.in "namespace interp"
```

## Step 2 — Generate the header

**This step: give the project a version, generate `version.h` from the template, and test `calc --version`.**

Three changes to `CMakeLists.txt`:

```cmake
project(interp VERSION 1.0.0 LANGUAGES CXX)
...
configure_file(cmake/version.h.in generated/interp/version.h)
...
target_include_directories(interp_core PUBLIC
    include
    ${CMAKE_CURRENT_BINARY_DIR}/generated)
```

- `project(... VERSION 1.0.0)` sets `PROJECT_VERSION`, and `PROJECT_VERSION_MAJOR`, `_MINOR`, `_PATCH`.
- `configure_file` copies the template, replacing `@VAR@` with each variable's value. A relative output path is inside the **build** folder, so the generated file is never committed: it's always made fresh from the one true number. It's rewritten only when its content changes, so a rebuild doesn't recompile everything.
- The `generated` folder is `PUBLIC` on `interp_core`, so `#include "interp/version.h"` works in the app.

Add a CTest test for the flag, which passes when the output matches a regular expression:

```cmake
add_test(NAME calc_version COMMAND calc --version)
set_tests_properties(calc_version PROPERTIES
    PASS_REGULAR_EXPRESSION "calc ${PROJECT_VERSION}")
```

Build, and look at the result: `build/generated/interp/version.h`. The test itself waits for the next step.

```cmake file=CMakeLists.txt
cmake_minimum_required(VERSION 3.20)
project(interp VERSION 1.0.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
# Write build/compile_commands.json, for clang-tidy and editors.
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

# Settings every target in this project uses. An INTERFACE library
# has no code: linking to it just passes its settings on.
add_library(interp_options INTERFACE)
if(MSVC)
    target_compile_options(interp_options INTERFACE /W4)
else()
    target_compile_options(interp_options INTERFACE -Wall -Wextra -Wpedantic)
endif()

option(SANITIZE "Build with ASan and UBSan" OFF)
if(SANITIZE)
    target_compile_options(interp_options INTERFACE
        -fsanitize=address,undefined -fno-omit-frame-pointer -g)
    target_link_options(interp_options INTERFACE
        -fsanitize=address,undefined)
endif()

# version.h, generated from the project's VERSION.
configure_file(cmake/version.h.in generated/interp/version.h)

# The interpreter: a library, shared by the app and the tests.
add_library(interp_core
    src/tokenizer.cpp
    src/parser.cpp
    src/interpreter.cpp)
target_include_directories(interp_core PUBLIC
    include
    ${CMAKE_CURRENT_BINARY_DIR}/generated)
target_link_libraries(interp_core PRIVATE interp_options)

# The program people run.
add_executable(calc app/main.cpp)
target_link_libraries(calc PRIVATE interp_core interp_options)

# The tests: ctest runs every add_test.
enable_testing()
file(GLOB TEST_SOURCES CONFIGURE_DEPENDS tests/*_test.cpp)
add_executable(interp_tests testing/test_main.cpp ${TEST_SOURCES})
target_include_directories(interp_tests PRIVATE testing)
target_link_libraries(interp_tests PRIVATE interp_core interp_options)
add_test(NAME unit_tests COMMAND interp_tests)

# calc itself: a line that works exits with 0; one that doesn't
# must fail (WILL_FAIL turns "exited with 1" into a pass).
add_test(NAME calc_accepts_a_line COMMAND calc "1 + 2 * 3")
add_test(NAME calc_rejects_bad_syntax COMMAND calc "1 +")
set_tests_properties(calc_rejects_bad_syntax PROPERTIES WILL_FAIL TRUE)
add_test(NAME calc_version COMMAND calc --version)
set_tests_properties(calc_version PROPERTIES
    PASS_REGULAR_EXPRESSION "calc ${PROJECT_VERSION}")

# Formatting: "format" rewrites the files, "check-format" only checks.
find_program(CLANG_FORMAT clang-format)
if(CLANG_FORMAT)
    file(GLOB_RECURSE FORMAT_SOURCES CONFIGURE_DEPENDS
        include/*.h src/*.cpp app/*.cpp tests/*.cpp)
    add_custom_target(format
        COMMAND ${CLANG_FORMAT} -i ${FORMAT_SOURCES}
        WORKING_DIRECTORY ${CMAKE_CURRENT_SOURCE_DIR})
    add_custom_target(check-format
        COMMAND ${CLANG_FORMAT} --dry-run --Werror ${FORMAT_SOURCES}
        WORKING_DIRECTORY ${CMAKE_CURRENT_SOURCE_DIR})
endif()
```

## Step 3 — calc --version

**This step: make `calc --version` print `calc 1.0.0`. Build, and run CTest.**

At the start of `main`:

```cpp
if (argc == 2 && std::string_view(argv[1]) == "--version") {
    std::cout << "calc " << interp::version << '\n';
    return 0;
}
```

`argv[1]` is a `char*`: comparing it with `==` to a literal compares **addresses**, never characters. `std::string_view(argv[1])` compares the text. Include `"interp/version.h"` and `<string_view>`.

```text
cmake --build build
./build/calc --version
ctest --test-dir build
```

**Experiment:** change the version in `project()` to `1.0.1` and build: `main.cpp` didn't change, yet `calc --version` follows. Put it back to `1.0.0`.

```cpp file=app/main.cpp
// calc: a calculator with variables.
//
//   calc "x = 6" "x * 7"   runs each argument as a line
//   calc                   reads lines until the input ends
//   calc --version         prints the version
#include "interp/interpreter.h"
#include "interp/tokenizer.h"
#include "interp/version.h"

#include <iostream>
#include <string>
#include <string_view>

namespace {

// Runs one line, printing "= value" or "error: why". Returns
// whether it worked.
bool run_line(interp::Interpreter& interpreter, const std::string& line)
{
    try {
        const double value = interpreter.execute(line);
        std::cout << "= " << value << '\n';
        return true;
    } catch (const interp::SyntaxError& e) {
        std::cout << "error: " << e.what() << '\n';
    } catch (const interp::EvalError& e) {
        std::cout << "error: " << e.what() << '\n';
    }
    return false;
}

bool is_blank(const std::string& line)
{
    return line.find_first_not_of(" \t\r") == std::string::npos;
}

} // namespace

int main(int argc, char* argv[])
{
    if (argc == 2 && std::string_view(argv[1]) == "--version") {
        std::cout << "calc " << interp::version << '\n';
        return 0;
    }

    interp::Interpreter interpreter;
    bool all_worked = true;
    if (argc > 1) {
        for (int i = 1; i < argc; ++i)
            all_worked = run_line(interpreter, argv[i]) && all_worked;
    } else {
        std::string line;
        while (std::getline(std::cin, line)) {
            if (!is_blank(line))
                all_worked = run_line(interpreter, line) && all_worked;
        }
    }
    return all_worked ? 0 : 1;
}
```

```check
run "./build/calc --version" stdout="calc 1.0.0"
run "ctest --test-dir build" stdout="100% tests passed"
```

## Step 4 — Install rules

**This step: add `install()` rules to `CMakeLists.txt`, then install into `build/stage` and run the installed program.**

Building leaves files scattered across `build/`. **Installing** copies just the ones users need into a standard layout under a **prefix**:

```text
<prefix>/bin/calc                       the program
<prefix>/share/doc/interp/README.md     its documentation
```

```cmake
install(TARGETS calc RUNTIME DESTINATION bin)
install(FILES README.md DESTINATION share/doc/interp)
```

- `install(TARGETS ...)` knows which file the target produced: `calc` or `calc.exe`. `RUNTIME` means executables (and Windows DLLs).
- Destinations are **relative**: the prefix is chosen at install time, `/usr/local` by default on Linux and macOS.
- The tests and the static library aren't installed. Users need the program, not your build.

```text
cmake --build build
cmake --install build --prefix build/stage
./build/stage/bin/calc --version
```

Installing into `build/stage` keeps this exercise inside the ignored build folder. For real, a package manager or `sudo cmake --install build` would use the system prefix.

## Step 5 — Packages with CPack

**This step: add CPack to `CMakeLists.txt` and build the `package` target.**

```cmake
set(CPACK_PACKAGE_NAME interp)
set(CPACK_GENERATOR "ZIP;TGZ")
include(CPack)
```

**CPack** does an install into a temporary folder, then packs it. `include(CPack)` must come **after** the `set`s and the `install()` rules: it reads them when it runs. The version comes from `project()` automatically.

| Generator | Makes |
|---|---|
| `ZIP`, `TGZ` | archives: unpack anywhere and run |
| `NSIS`, `WIX` | Windows installers |
| `DragNDrop` | a macOS `.dmg` |
| `DEB`, `RPM` | Linux packages for `apt` and `dnf` |

```text
cmake --build build
cmake --build build --target package
```

```text
CPack: - package: .../build/interp-1.0.0-Linux.zip generated.
CPack: - package: .../build/interp-1.0.0-Linux.tar.gz generated.
```

The system name in the file name (`Linux`, `win64`, `Darwin`) says where it was built: a package holds compiled code for one system. That's why release pipelines build packages on each system, the way the CI matrix tests on each.

## Step 6 — Tag the release

**This step: commit, then tag the commit `v1.0.0`.**

```text
git status
git add -A
git commit -m "Release 1.0.0: --version, install rules, packages"
git tag -a v1.0.0 -m "interp 1.0.0"
git log --oneline --decorate -3
```

A **tag** is a name fixed to one commit, forever. A branch moves with each new commit; a tag never does. `-a` makes an **annotated** tag, which records who tagged it, when, and a message, like a commit does. Releases use annotated tags; the `v` prefix is the common convention.

- `git checkout v1.0.0` gets back the exact source of this release, even years and thousands of commits later. That's how you reproduce a bug a user reports in 1.0.0.
- `git describe` names any commit relative to the latest tag: `v1.0.0-3-g1a2b3c4` means "3 commits after v1.0.0".
- Tags aren't pushed by default: `git push origin v1.0.0`.

Tag **after** the commit: a tag on the previous commit would name a release without its own version number in it.

```check
git-clean
git-tag v1.0.0 -- git tag -a v1.0.0 -m "interp 1.0.0"
git-message "1.0.0"
```

## Step 7 — Where releases go from here

**This step: read, then try the challenges. No checks. Steps 8 and 9 are the track's last required task.**

In a real project the last mile is automated too. A second workflow runs when a tag is pushed, builds the packages on each system, and attaches them to a GitHub **release**:

```yaml
on:
  push:
    tags: ['v*']
jobs:
  package:
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - run: cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
      - run: cmake --build build --config Release
      - run: cpack --config build/CPackConfig.cmake -C Release
      - uses: softprops/action-gh-release@v2
        with:
          files: interp-*
```

Nobody builds a release on their own laptop, so every release is built the same way, from the tagged source.

### Challenges

1. Keep a `CHANGELOG.md`: under a heading per version, list what was **Added**, **Changed** and **Fixed**, written for users, not developers. Write the 1.0.0 entry from `git log --oneline`.
2. Add a `CMakePresets.json` with `default` and `asan` presets, so `cmake --preset asan` replaces the long configure command. Use the presets in `ci.yml`.
3. Make CI build with both GCC and Clang on Ubuntu (a second matrix dimension, `compiler: [g++, clang++]`, passed as `-DCMAKE_CXX_COMPILER`). Which lesson's bug would Clang's warnings have caught?

## Step 8 — Your change: a remainder operator

**This step: no code is given. Add a `%` operator to interp, tests first, on a branch, and merge it into `main`.**

Every practice in this track was shown to you first. This change uses all of them, and you decide the order of the work. `a % b` is the remainder after dividing `a` by `b`:

| Line | Result |
|---|---|
| `7 % 3` | `= 1` |
| `-7 % 3` | `= -1` (the sign follows the left side, as C++'s `std::fmod` does) |
| `7.5 % 2` | `= 1.5` (numbers aren't only whole) |
| `1 + 7 % 3 * 2` | `= 3` (`%` has the rank of `*` and `/`, and groups left to right) |
| `5 % 0` | `error: division by zero`, and `calc` exits with 1 |

The work, in the order a reviewer expects to see it:

1. `git switch -c feature/remainder`.
2. Write `tests/remainder_test.cpp` first, with at least three tests, one of them for remainder by zero (`CHECK_THROWS`, like `division_by_zero_is_an_error`). Build and watch them fail: a test you've never seen fail might not test anything.
3. Make them pass. Three layers change: the tokenizer, the parser's `term`, and the interpreter. Follow how `/` goes through each.
4. Run every test. One test written in lesson 1 now fails: find it, and decide whether your code or that test is wrong. When a behaviour changes on purpose, the test that pinned down the old behaviour changes with it, in the same commit, and the commit message says why.
5. Run `ctest`, commit, switch to `main`, and merge the branch.

**Before you merge, review your own change** the way a colleague would:

- Does each commit message say what changed and why?
- Is there a test that would fail if `%` had the rank of `+`? One that would fail if it threw away the fraction?
- Does `-7 % 3` give what the table says, and do you know why?
- Is anything in the diff unrelated to `%`? (`git diff main` shows it all.)

```check
git-has-branch feature/remainder -- git switch -c feature/remainder
matches tests/remainder_test.cpp "(\bTEST(_F)?\s*\([\s\S]*){3}" label="remainder_test.cpp has at least three tests"
matches tests/remainder_test.cpp "%\s*0\b" label="a test takes a remainder by zero"
run "cmake --build build"
tests "./build/interp_tests"
run "./build/calc \"7 % 3\" \"-7 % 3\" \"7.5 % 2\" \"1 + 7 % 3 * 2\"" stdout="= 1\n= -1\n= 1.5\n= 3" label="calc gets the four remainders in the table right"
run "./build/calc \"5 % 0\"" exit=1 stdout="error: division by zero" label="a remainder by zero is an error"
git-branch main -- Switch back to main and merge: git switch main, then git merge feature/remainder
git-merged feature/remainder main
git-clean
```

## Step 9 — Release 1.1.0

**This step: no code is given. Release your change as version 1.1.0: the version number, a changelog entry, a commit and a tag, all on `main`.**

- **The version.** `%` adds something new and breaks nothing that worked before. Under semantic versioning that's a MINOR change: 1.0.0 becomes 1.1.0. (A PATCH, 1.0.1, would only fix a bug; a MAJOR, 2.0.0, would change behaviour people rely on.) There is one place to change it, from step 1.
- **`CHANGELOG.md`.** Create it with a `## 1.1.0` heading and, under **Added**, one line about `%` written for someone who uses calc, not for someone who reads its code.
- **Commit and tag**, as in step 6: the commit message names the version, and the tag `v1.1.0` goes on that commit.

`calc --version` should now print `calc 1.1.0`, and `ctest` should still pass: its version test compares against the project's version, so it moved with it.
