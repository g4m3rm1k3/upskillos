Listing every task was a useful first implementation but an unbounded product behavior. We add a bounded search endpoint and examine its query plan. An index is a data structure with write and storage costs, not a magic speed switch.

## Validate query cost at the boundary

```predict
question: A LIKE query binds a user-supplied percent sign as a parameter. Does parameter binding make it a literal percent match?
choice: Yes, parameter binding removes all special meanings.
choice: No, LIKE still interprets pattern wildcards.
answer: No, LIKE still interprets pattern wildcards.
explain: Binding separates values from SQL syntax, but the LIKE operation still interprets its value as a pattern. Literal substring search additionally escapes percent, underscore and the chosen escape character.
```

### Distinguish SQL parameters from LIKE pattern syntax

A URL such as /api/search?q=fix&limit=25&offset=0 carries named query parameters. RequestParam binds them to method arguments and converts numeric text to int. defaultValue supplies values when a parameter is omitted or empty. The guard rejects excessive page size, negative offset and excessive query length before issuing SQL.

SQL LIKE has its own pattern language: percent matches any sequence and underscore matches one character. Binding a parameter prevents SQL injection, but does not turn these pattern symbols into literal characters. We must separately define whether users requested wildcard search or literal substring search. This endpoint promises literal text.

Follow a query `50%_done!`: lowercasing with Locale.ROOT avoids using the machine's default locale. Replace ! with !! first so existing escape characters are protected. Replace % with !% and _ with !_. Surround the result with percent signs to allow any prefix and suffix. The final pattern is `%50!%!_done!!%`. The SQL ESCAPE clause assigns ! this escape role.

Order matters: escaping ! last would also double the escape characters just introduced for % and _, changing their meaning. **Predict:** binding `literal%marker` without pattern escaping matches literalXmarker too. The later test uses those two titles to distinguish safe parameter binding from correct search semantics.

Query parameters are user input, even when generated by your own UI. We bound result size and query length. Locale.ROOT makes normalization independent of machine locale. LIKE has wildcard syntax, so escaping percent, underscore and the escape character gives literal substring search instead of accidentally exposing wildcard behavior.

The leading percent permits a substring anywhere in the title; a conventional title index may not accelerate it. Record that limitation before adding an index based on intuition.

```java edit=src/main/java/workspace/SearchController.java mode=replace
package workspace;
import org.springframework.web.bind.annotation.*;
import org.springframework.jdbc.core.JdbcTemplate;
import java.util.*;

@RestController
public class SearchController {
    private final JdbcTemplate jdbc;
    public SearchController(JdbcTemplate jdbc) { this.jdbc = jdbc; }
    @GetMapping("/api/search")
    public List<Task> search(@RequestParam(defaultValue="") String q,
        @RequestParam(defaultValue="25") int limit, @RequestParam(defaultValue="0") int offset) {
        if (limit < 1 || limit > 100 || offset < 0 || q.length() > 80)
            throw new IllegalArgumentException("Invalid search bounds");
        String pattern = "%" + q.toLowerCase(Locale.ROOT).replace("!", "!!").replace("%", "!%").replace("_", "!_") + "%";
```

## Return a deterministic bounded page

### Read the query in logical stages

FROM chooses tasks; WHERE retains rows whose lowercased title matches the pattern; ORDER BY id establishes an order; OFFSET skips that many ordered rows; LIMIT caps the number returned. The parameter sequence follows the placeholders: pattern, limit, offset. The row mapper is the same representation conversion taught in JdbcTasks.

For a fixed ordered result [A,B,C,D], limit 2 and offset 0 returns A,B; offset 2 returns C,D. Insert a new row before A between reads, and offset 2 can now return B,C. Deterministic ordering does not create a snapshot shared across separate requests. A pagination design must state how it handles changing data.

A return limit bounds response size, not necessarily database work. Leading-wildcard substring search may inspect many rows to find matches, and a large offset can still be expensive. Inspect the query plan and representative workload before claiming bounded output means bounded execution cost.

Parameters bind the search term and bounds. Ordering makes a page reproducible for a fixed dataset, but concurrent inserts can shift offset pages. Keyset pagination uses the last seen ordering key to avoid deep offset scans; it changes the client contract and is not always necessary for a small board.

In Board.tsx replace both read URLs `/api/tasks` with `/api/search?limit=25`. Keep POST creation pointed at `/api/tasks`. Add a visible sentence below the heading: `<p>Showing the first 25 tasks. Search is available through the API.</p>`. This makes the UI's current bound honest instead of hiding omitted records. A complete search interface is a capstone option.

## Verify literal search and limits

### Identify what the near-miss data distinguishes

The two titles differ at one position: a literal percent versus X. A wildcard interpretation would match both for literal%marker. Our required literal interpretation matches only one, so size 1 distinguishes the two behaviors. Querying with an unrelated title would not exercise escaping at all.

The empty-query limit-one assertion checks response size, while invalid limit and offset assertions check rejected inputs. Calling search directly still uses the injected real datasource but bypasses HTTP parameter conversion and the security filter chain. It cannot establish that the correct role may invoke the route or that a nonnumeric limit gets the right HTTP response.

Use a disposable dataset for timing. Record row count, query text, parameters, plan and repeated timings before comparing an index. A fast query on two rows establishes little about a large dataset. A result limit can cap returned objects while the database still scans many rows, so inspect the plan rather than inferring cost from response length.

This test invokes the controller through Spring's real datasource but does not test HTTP binding. Keep the API tests for that boundary. The two similar titles distinguish literal percent behavior from a wildcard match.

Measure with representative data in a disposable database. Use EXPLAIN on the generated SQL and compare row counts, latency and write cost before and after an index. A tiny warm-cache timing is not evidence about a large production workload.
