A release is a reproducible result with evidence, configuration and a recovery plan. “It ran in my editor” leaves the environment and exact source ambiguous. We build frontend assets before packaging the Java archive so the release contains the interface learners actually tested.

## Declare repeatable CI preparation

### Read the workflow as a graph of jobs and steps

YAML uses indentation to nest mappings and lists. `name:` labels the workflow. `on: [push, pull_request]` chooses repository events that start it. `permissions` narrows the workflow token's repository access. Under jobs, verify is our job identifier; runs-on chooses its runner environment.

Each hyphen under steps begins one sequential step. `uses` invokes a reusable action, while `with` supplies that action's named inputs. Checkout obtains the source revision being verified. setup-java selects JDK 21; setup-node selects the Node runtime. Quoting version numbers prevents them being misinterpreted as numeric values by configuration tooling.

The npm cache key uses frontend/package-lock.json to relate cached downloads to dependency resolution. A cache is an optimization, not a replacement for installing dependencies. **Predict:** a workflow that passes only when a previous run populated its cache is not reproducible from its declared inputs. Test from a clean checkout when investigating that failure.

CI starts from a checkout instead of your working directory. The runner image supplies tooling, while setup actions select the language runtimes. Read-only repository permissions are sufficient for verification. Dependency caching improves speed; it must not be required for correctness.

Major action tags are readable teaching references but can move; a stricter supply-chain policy pins reviewed commit hashes and automates updates. That choice trades auditability against maintenance effort.

Type this fragment yourself. Start an empty file at `.github/workflows/verify.yml`:

```yaml edit=.github/workflows/verify.yml mode=replace
name: Verify Common Ground
on: [push, pull_request]
permissions:
  contents: read
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
      - uses: actions/setup-node@v4
        with:
          node-version: '22.14.0'
          cache: npm
          cache-dependency-path: frontend/package-lock.json
```

## Build in dependency order

### Explain why rearranging these commands changes the artifact

A run step launches a shell command on the checked-out source. npm ci installs from the committed lockfile. npm test executes the frontend component suite. npm run build typechecks and generates static assets into Java's resource tree. Maven verify then compiles, tests and packages the Java application, including those newly generated resources.

If Maven packages first, the JAR can contain old or missing frontend files even when Vite builds successfully afterward. The dependency is between outputs and inputs, not just an arbitrary preferred order. The artifact-upload action stores the named JAR from target so the verified output can be retrieved without rebuilding different source later.

**Experiment:** inspect the archive's file list after building and find app/index.html and its generated asset files. Then compare those paths with the browser's Network requests while running the JAR. This crosses the packaging boundary that isolated frontend and Java tests cannot fully establish.

The lockfile must be committed for npm ci. The frontend build writes static assets before Maven packages resources. Verify runs tests and packaging lifecycle stages; -B selects noninteractive output. The artifact is the output to deploy, not a fresh rebuild from an unknown checkout.

Append `src/main/resources/static/app/` to .gitignore because these files are generated by the frontend build. Commit source and lockfiles, not the generated assets. Run these same commands locally before pushing your learning repository.

Type this fragment yourself. Append to `.github/workflows/verify.yml`:

```yaml edit=.github/workflows/verify.yml mode=append
      - run: npm ci --prefix frontend
      - run: npm test --prefix frontend
      - run: npm run build --prefix frontend
      - run: mvn -B verify
      - uses: actions/upload-artifact@v4
        with:
          name: common-ground
          path: target/common-ground-1.0.0.jar
```

```check
run "npm run build --prefix frontend" timeout=180
run "mvn -q verify" timeout=180
```

## Run the packaged application

### Perform the release smoke test in a repeatable order

A **smoke test** checks a small set of critical behaviors through the assembled system. It complements detailed unit and integration tests. Use a disposable course database and a locally chosen development credential. Record the archive's build revision and the directory from which you launch it, because the default database path is relative to that directory.

1. Stop Vite and any Java development process. Build frontend assets, then run Maven verify. Start the resulting JAR with the required environment setting. This ensures the browser cannot accidentally use a still-running development server.
2. Visit http://localhost:8080/login. Sign in as editor using your local credential. Expect the browser to reach /app/ and the board to finish loading. Inspect the Network panel for successful HTML, script, stylesheet and API requests. A blank UI with successful HTML is not a pass.
3. Create a uniquely named task such as `Release rehearsal`. Expect one visible TODO task, then advance it to DOING. Expand Discussion, type a comment, send it, and verify the displayed author is editor. Record the task's id from the API response, not a cookie or token.
4. Open a second tab at the same application origin and load the board in both tabs. Both should display the same revision. Advance the task in tab A, then try the old Advance action in tab B. Expect conflict feedback, not a second accepted stale command. Refresh B and confirm it displays the accepted state.
5. Stop the Java process cleanly with Ctrl+C. Restart the same JAR from the same directory against the same database. Sign in again, find the task, load its comments, and confirm both persisted. A browser's cached state is insufficient; inspect the new API read.
6. Open a private browser window and request /api/tasks without signing in. Expect the API's 401 behavior. Separately submit an incorrect login password and confirm it does not establish an authenticated session.
7. Use Tab and Enter to create another disposable task without a mouse. Inspect visible focus and status feedback at a narrow viewport. Record any failure as remaining release work, even if automated tests are green.
8. Match an observed X-Request-Id response header with its server log entry. Stop the process when the rehearsal is complete.

If there are more than the board's displayed first page of tasks, use a fresh disposable database for this rehearsal. The current UI explicitly shows its bound; it does not implement search pagination controls. Do not mistake an omitted page item for a failed INSERT without inspecting the response/API.

### Rehearse recovery without risking your learning data

For this local H2 release, stop the process before copying its database file into a separate backup location. Record the filename and a release identifier. Make changes only in a disposable rehearsal copy, then stop again and restore that copy from the backup. Start against the restored path and verify the earlier task and comment state. Copying a live database file is not the backup procedure taught here.

Application rollback and data restore are different actions. Re-running an older JAR changes executable behavior; restoring a backup replaces durable state with an earlier snapshot and can lose newer accepted writes. Our description migration was an isolated experiment, so it has not silently changed this release's database. For future deployed migrations, consult the compatibility matrix before choosing rollback.

Write operations/release.md with the source revision, runtime versions, exact build/start commands without secrets, database path, observed results, known limits and recovery evidence. Another learner should be able to reproduce the release from that record and the source repository.

Stop the development server. With your local WORKSPACE_PASSWORD set, run:

```text
java -jar target/common-ground-1.0.0.jar
```

Open `/login`, sign in, and visit `/app/`. Create a task, advance it, add a comment, restart and verify persistence. Inspect the built asset paths in the Network panel. A working Vite development server does not prove packaged asset paths are correct.

Before deploying elsewhere, decide TLS termination, secret injection, database ownership, backups, log retention, resource limits and dependency patch policy. The bundled H2 database is for this local learning release. A hosted shared service needs an explicit database and identity deployment design.

Record the Git commit, build commands and observed smoke test in `operations/release.md`. Stop the process when done.

