A system needs evidence when it fails outside the debugger. Logs record events; metrics aggregate behavior; traces connect work across boundaries. Useful diagnostics answer a question without exposing passwords, session tokens or task content unnecessarily.

## Record request outcome and duration

### Identify the inherited callback

`extends OncePerRequestFilter` makes RequestLog a subclass of Spring's filter base class. The framework calls our overridden doFilterInternal during request handling; our code does not call it from main. `protected` allows the inherited framework mechanism to use this method without making it a general application entry point.

HttpServletRequest exposes the incoming request; HttpServletResponse exposes the outgoing response; FilterChain represents the remaining processing to invoke. The throws clause declares checked failures permitted to propagate. @Component makes the filter discoverable as a managed object.

Generate a UUID per observed request and put it in X-Request-Id before passing control onward. A client can quote that id to connect its observation with a server log entry. Record System.nanoTime before handling so a later difference measures elapsed time rather than calendar time. The raw number is not a timestamp a human should interpret as a date.

A servlet filter wraps request processing. The request id is generated by our server rather than trusting arbitrary client text. NanoTime measures elapsed duration using a monotonic source; wall-clock changes should not distort a latency measurement. The response header lets a user quote an id when reporting failure.

A filter's position matters: some security rejections may occur before an application filter. Verify which requests your instrumentation covers before treating it as complete traffic accounting.

Type this fragment yourself. Start an empty file at `src/main/java/workspace/RequestLog.java`:

```java edit=src/main/java/workspace/RequestLog.java mode=replace
package workspace;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;
import jakarta.servlet.*;
import jakarta.servlet.http.*;
import java.io.IOException;
import java.util.UUID;
import org.slf4j.LoggerFactory;

@Component
public class RequestLog extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
        FilterChain chain) throws ServletException, IOException {
        String id = UUID.randomUUID().toString();
        long start = System.nanoTime();
        response.setHeader("X-Request-Id", id);
```

## Log bounded metadata after handling

### Trace control leaving and reentering the filter

`chain.doFilter(request, response)` invokes the remaining filters and request handling. This call can return normally or throw. Java executes finally in either case, so timing is attempted even when the normal flow failed. Finally does not swallow the original exception unless it itself throws or returns; our code does neither intentionally.

Subtract start from a second nanoTime sample and divide by 1000 to express nanoseconds as microseconds. Both are long integers, so division discards fractional microseconds. For a 2,345,678-nanosecond difference the logged value is 2345. This precision is adequate for our diagnostic example but should be stated rather than implied exact.

LoggerFactory.getLogger selects a logger associated with this class. info submits the message at the information level. The four `{}` placeholders correspond in order to id, request method, current response status and elapsed microseconds. This placeholder syntax belongs to the logging library; it is not Java string interpolation.

**Predict:** if an exception is translated to a final response after this filter unwinds, getStatus here can be earlier than the final client status. Compare a known handled validation error and an unhandled failure before using the log as complete error accounting. Instrumentation has a location and a contract just as application code does.

Finally records timing on both success and failure. Parameterized logging separates the message template from values. We omit request bodies, cookies and authorization headers. Even this log needs retention and access policy in a real service.

Run the application, trigger a successful read and an invalid write, and match a response id with a log entry. A servlet exception can be translated after a filter unwinds, so do not assume this early status is authoritative for every unhandled failure. Test the failure paths you intend to monitor.

Type this fragment yourself. Append to `src/main/java/workspace/RequestLog.java`:

```java edit=src/main/java/workspace/RequestLog.java mode=append
        try { chain.doFilter(request, response); }
        finally {
            long micros = (System.nanoTime() - start) / 1000;
            LoggerFactory.getLogger(RequestLog.class).info(
                "request={} method={} status={} durationMicros={}",
                id, request.getMethod(), response.getStatus(), micros);
        }
    }
}
```

## Write an incident runbook

### Turn a symptom into a discriminating observation

Use a short decision table in the runbook. For “page loads but tasks do not,” check the API response: 401 directs you toward session state; 409 follows a rejected stale command; no response directs you toward listening address/proxy/process state. Include the exact place to look and a reversible next action, not just a list of possible causes.

For “database locked,” identify the other process holding the same file before stopping anything. For “schema mismatch,” compare the deployed artifact and effective database path/migration state before attempting another migration. Capture a request id and timestamps without recording cookies, secrets or user content.

A **percentile** describes a position in ordered measurements. The 95th percentile is a value at or below which roughly 95% of observed durations fall under the chosen calculation. It can expose a slow tail hidden by the mean. State the measurement window and workload: a latency objective without load or success criteria is ambiguous.

End each runbook branch with a recovery check. A restarted process is not enough; verify an authenticated read and a deliberate disposable write through the same path users use. That closes the loop between operational action and restored behavior.

Create `operations/runbook.md` with symptoms, evidence and reversible actions. Include: process not listening, database file locked, authentication rejected, repeated 409 conflicts, and a schema mismatch after deployment.

For each symptom state one observation that discriminates likely causes. “Restart everything” destroys evidence and can repeat the failure. A database lock should lead you to inspect competing processes; a stale revision should lead you to inspect client snapshots.

Define a service objective in user terms, such as successful task reads within an agreed latency under a stated workload. Choose error-rate and latency percentiles to observe it. An average can hide a slow tail. This course's log filter is a starting instrument, not a complete metrics platform.
