A system needs evidence when it fails outside the debugger. Logs record events; metrics aggregate behavior; traces connect work across boundaries. Useful diagnostics answer a question without exposing passwords, session tokens or task content unnecessarily.

## Record request outcome and duration

A servlet filter wraps request processing. The request id is generated by our server rather than trusting arbitrary client text. NanoTime measures elapsed duration using a monotonic source; wall-clock changes should not distort a latency measurement. The response header lets a user quote an id when reporting failure.

A filter's position matters: some security rejections may occur before an application filter. Verify which requests your instrumentation covers before treating it as complete traffic accounting.

Type this fragment yourself. Start an empty file at `src/main/java/workspace/RequestLog.java`:

```java edit=src/main/java/workspace/RequestLog.java mode=replace
package workspace;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;
import jakarta.servlet.*;
import jakarta.servlet.http.*;
import java.io.IOException;
import java.util.UUID;
import org.slf4j.LoggerFactory;

@Component
public class RequestLog extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
        FilterChain chain) throws ServletException, IOException {
        String id = UUID.randomUUID().toString();
        long start = System.nanoTime();
        response.setHeader("X-Request-Id", id);
```

## Log bounded metadata after handling

Finally records timing on both success and failure. Parameterized logging separates the message template from values. We omit request bodies, cookies and authorization headers. Even this log needs retention and access policy in a real service.

Run the application, trigger a successful read and an invalid write, and match a response id with a log entry. A servlet exception can be translated after a filter unwinds, so do not assume this early status is authoritative for every unhandled failure. Test the failure paths you intend to monitor.

Type this fragment yourself. Append to `src/main/java/workspace/RequestLog.java`:

```java edit=src/main/java/workspace/RequestLog.java mode=append
        try { chain.doFilter(request, response); }
        finally {
            long micros = (System.nanoTime() - start) / 1000;
            LoggerFactory.getLogger(RequestLog.class).info(
                "request={} method={} status={} durationMicros={}",
                id, request.getMethod(), response.getStatus(), micros);
        }
    }
}
```

## Write an incident runbook

Create `operations/runbook.md` with symptoms, evidence and reversible actions. Include: process not listening, database file locked, authentication rejected, repeated 409 conflicts, and a schema mismatch after deployment.

For each symptom state one observation that discriminates likely causes. “Restart everything” destroys evidence and can repeat the failure. A database lock should lead you to inspect competing processes; a stale revision should lead you to inspect client snapshots.

Define a service objective in user terms, such as successful task reads within an agreed latency under a stated workload. Choose error-rate and latency percentiles to observe it. An average can hide a slow tail. This course's log filter is a starting instrument, not a complete metrics platform.
