# Lesson 18: Sprites and CanvasTexture — Billboards and Procedural Textures

What you will build
In this lesson, you will build 2D elements that exist within our 3D Three.js world. You will learn to use `THREE.Sprite` to create "billboards"—images or textures that always face the camera—and `THREE.CanvasTexture` to draw dynamic 2D text, health bars, and procedural gradients using the standard HTML Canvas API, bringing them seamlessly into the 3D scene without needing external image files.

What you need to know first
- Lesson 17 for understanding how materials and textures are applied to meshes.

Terms used in this lesson
- **Billboard** — A 2D object in a 3D scene that constantly rotates to face the camera, ensuring it is always visible flat-on.
- **Procedural texture** — A texture that is generated by code rather than loaded from a static image file like a PNG or JPEG.
- **Additive blending** — A rendering technique where the colors of overlapping transparent objects are added together, creating a brighter result.
- **Depth buffer** — A memory structure that keeps track of the distance of each pixel from the camera to determine which objects occlude others.
- **Perspective scale** — The visual effect where objects appear smaller as they move further away from the camera.

Objects and methods used
- **`THREE.Sprite`**
  - *What it is:* A 3D object representing a plane that always faces the camera.
  - *Implementation:* `new THREE.Sprite(material)`
  - *Its use:* To display 2D labels or particles that should always be readable or visible.
  - *Type:* Class instance extending `THREE.Object3D`.
  - *Responsibility:* Manages its own rotation internally to continually orient its plane towards the active camera.
  - *Depends on:* A `THREE.SpriteMaterial` to define its visual appearance.
  - *Connects to:* Added to a `THREE.Scene`, rendered by `THREE.WebGLRenderer`.
  - *Shape:* A leaf node in the scene graph.
- **`THREE.SpriteMaterial`**
  - *What it is:* A specialized material used exclusively with `THREE.Sprite`.
  - *Implementation:* `new THREE.SpriteMaterial({ color: 0xff4400, sizeAttenuation: true })`
  - *Its use:* To apply textures and colors to sprites while controlling properties like transparency.
  - *Type:* Class instance extending `THREE.Material`.
  - *Responsibility:* Provides shader parameters specific to sprites, such as `sizeAttenuation` and texture maps.
  - *Depends on:* Optionally a `THREE.Texture` and color properties.
  - *Connects to:* Attached to a `THREE.Sprite`.
  - *Shape:* Data object passed during sprite instantiation.
- **`THREE.CanvasTexture`**
  - *What it is:* A texture created from an HTML `<canvas>` element.
  - *Implementation:* `new THREE.CanvasTexture(canvasElement)`
  - *Its use:* To use procedurally drawn 2D graphics as textures in Three.js.
  - *Type:* Class instance extending `THREE.Texture`.
  - *Responsibility:* Uploads the pixel data from a 2D canvas to the GPU for use in WebGL shaders.
  - *Depends on:* A populated HTML `<canvas>` element.
  - *Connects to:* Assigned to the `map` property of a `THREE.Material`.
  - *Shape:* A bridge between the browser's 2D Canvas API and WebGL textures.
- **`needsUpdate`**
  - *What it is:* A boolean flag on Three.js textures.
  - *Implementation:* `texture.needsUpdate = true;`
  - *Its use:* To tell the renderer that the source data has changed and must be re-uploaded to the GPU.
  - *Type:* Boolean property on `THREE.Texture`.
  - *Responsibility:* Triggers a texture refresh during the next render cycle.
  - *Depends on:* The underlying source data being modified before the flag is set.
  - *Connects to:* Read by `THREE.WebGLRenderer` to manage GPU memory.
  - *Shape:* State invalidation flag.

## Concept Unit: THREE.Sprite — always-facing-camera quad

### The Problem
When placing text or 2D icons in a 3D world (like a health bar over a character's head), a standard flat plane will become unreadable if the camera moves around to its side or back. How do we ensure a 2D element always directly faces the camera so it is always legible?

### Introduce the concept in isolation
```html
<!DOCTYPE html>
<html>
<body>
<script type="module">
import * as THREE from 'three';
// Sprite: a plane that always rotates to face the camera
// No geometry needed: Three.js handles the billboard rotation internally
const spriteMat = new THREE.SpriteMaterial({
    color: 0xff4400,
    sizeAttenuation: true,  // true=perspective scale, false=fixed screen size
});
const sprite = new THREE.Sprite(spriteMat);
sprite.position.set(0, 2, 0);
sprite.scale.set(0.5, 0.5, 1);  // width=0.5, height=0.5 world units
console.log('Sprite type:', sprite.type);          // 'Sprite'
console.log('Is billboard:', sprite.isSprite);     // true
console.log('Scale:', sprite.scale);               // Vector3(0.5, 0.5, 1)
</script>
</body>
</html>
```
Output:
```
Sprite type: Sprite
Is billboard: true
Scale: Object { x: 0.5, y: 0.5, z: 1 }
```
This output proves that `THREE.Sprite` is a distinct object type with an intrinsic billboard property. It is called a **Sprite**. The GPU renders a unit quad (2 triangles) in screen space, automatically applying billboard rotation so it always faces the camera. No `isMesh=true` is present, because it is not a standard Mesh. With `sizeAttenuation=true`, a perspective divide is applied, so a sprite at distance 10 appears half the size of a sprite at distance 5.

  Adds the sprite to the scene to be rendered.

### CS lens
A "billboard" is a classic computer graphics technique. Instead of computing complex 3D text geometry, we render a flat rectangle and apply a simple mathematical transformation in the vertex shader: we multiply the camera's inverse rotation matrix against the quad's vertices. This guarantees the quad's normal vector always points exactly parallel to the camera's viewing direction.

### SE lens
Using `sizeAttenuation` is a design decision about interface meaning. Setting it to `false` creates UI overlays (like crosshairs or screen-fixed labels) because the sprite remains a constant pixel size. Setting it to `true` anchors the sprite into the physical 3D world (like a damage number popping out of an enemy), tying its visual size to its 3D depth.

## Concept Unit: CanvasTexture — drawing text and shapes in 2D for use in 3D

### The Problem
We want to display text dynamically (like "Player 1: 42pts"). Generating 3D text geometry is computationally heavy, and baking every possible string into a PNG file is impossible. How can we leverage the browser's built-in 2D text rendering inside our 3D WebGL scene?

### Introduce the concept in isolation
```html
<!DOCTYPE html>
<html>
<body>
<script type="module">
import * as THREE from 'three';
function makeTextSprite(text, {fontSize=48, color='#ffffff', bgColor='rgba(0,0,0,0.6)'}={}) {
    const canvas = document.createElement('canvas');
    canvas.width = 512; canvas.height = 128;
    const ctx = canvas.getContext('2d');
    
    ctx.fillStyle = bgColor;
    ctx.roundRect(4, 4, 504, 120, 12);
    ctx.fill();
    
    ctx.fillStyle = color;
    ctx.font = `bold ${fontSize}px Arial`;
    ctx.textAlign = 'center';
    ctx.textBaseline = 'middle';
    ctx.fillText(text, 256, 64);
    
    const texture = new THREE.CanvasTexture(canvas);
    const mat = new THREE.SpriteMaterial({map: texture, transparent: true});
    const sprite = new THREE.Sprite(mat);
    sprite.scale.set(2, 0.5, 1);  // aspect ratio matches canvas 512:128 = 4:1, scaled 2:0.5
    return sprite;
}
const label = makeTextSprite('Player 1: 42pts');
console.log('Canvas size:', 512, 'x', 128);
console.log('Sprite has texture:', label.material.map !== null);
</script>
</body>
</html>
```
Output:
```
Canvas size: 512 x 128
Sprite has texture: true
```
This code creates a standard HTML canvas, draws a rounded rectangle and text onto it, and passes it to `THREE.CanvasTexture`. This is called a **CanvasTexture**. The pixels of the canvas are uploaded to the GPU, and we apply that texture to the sprite's material. The sprite's scale `(2, 0.5, 1)` maintains the 4:1 aspect ratio of the 512x128 canvas, preventing the text from appearing squished or stretched in world space.

## Concept Unit: Particle sprites — many sprites for effects

### The Problem
Visual effects like fire, magic spells, or glowing orbs require dozens of soft, glowing particles. If we draw a gradient on a canvas, how do we efficiently display 50 overlapping particles without them blocking each other out in the depth buffer?

### Introduce the concept in isolation
```html
<!DOCTYPE html>
<html>
<body>
<script type="module">
import * as THREE from 'three';
function makeGlowTexture() {
    const canvas = document.createElement('canvas');
    canvas.width = canvas.height = 64;
    const ctx = canvas.getContext('2d');
    const gradient = ctx.createRadialGradient(32, 32, 0, 32, 32, 32);
    gradient.addColorStop(0,   'rgba(255,255,255,1)');
    gradient.addColorStop(0.4, 'rgba(255,200,100,0.8)');
    gradient.addColorStop(1,   'rgba(255,100,0,0)');
    ctx.fillStyle = gradient;
    ctx.fillRect(0, 0, 64, 64);
    return new THREE.CanvasTexture(canvas);
}
const glowTex = makeGlowTexture();
const spriteMat = new THREE.SpriteMaterial({
    map: glowTex,
    transparent: true,
    blending: THREE.AdditiveBlending,  // additive: bright particles add up
    depthWrite: false,  // don't write to depth buffer (transparent particles)
});
const particles = [];
for (let i = 0; i < 50; i++) {
    const s = new THREE.Sprite(spriteMat.clone());
    particles.push(s);
}
console.log('Particle count:', particles.length);  // 50
console.log('Material depthWrite:', spriteMat.depthWrite); // false
</script>
</body>
</html>
```
Output:
```
Particle count: 50
Material depthWrite: false
```
This demonstrates rendering a batch of sprites. The canvas uses a radial gradient to create a soft, glowing circle. We configure the material with `blending: THREE.AdditiveBlending` and `depthWrite: false`. This is called **Additive blending**. When these transparent particles overlap, their color values add together to create a brighter core, and because they do not write to the depth buffer, they do not accidentally occlude other particles rendered behind them.

### Mechanical walkthrough
- **`ctx.createRadialGradient(32, 32, 0, 32, 32, 32)`**
  Creates a circular gradient starting from the center `(32, 32)` radiating outward to the edge `(radius 32)`.
- **`gradient.addColorStop(...)`**
  Defines the colors along the gradient: white in the very center, fading to semi-transparent orange, and finally fully transparent at the outer edge.
- **`blending: THREE.AdditiveBlending`**
  Instructs the WebGL renderer to add the color values of the sprite to whatever is already drawn behind it, creating intense highlights where sprites overlap.
- **`depthWrite: false`**
  Tells the GPU not to record this sprite's depth into the depth buffer. This prevents transparent edges from invisiblely hiding objects further back.
- **`glowMat.clone()`**
  Creates an independent copy of the material for each sprite. If we didn't clone it, modifying the opacity of one particle later would affect all 50.
- **`s.scale.setScalar(...)`**
  Sets the X, Y, and Z scale to the same randomly generated value simultaneously.

### CS lens
The depth buffer (Z-buffer) tracks the distance of the nearest drawn pixel. When rendering transparent objects, if an object closer to the camera is drawn first, it writes its depth. A transparent object drawn behind it later will be discarded by the GPU's depth-test, creating ugly hard cuts. Setting `depthWrite: false` is the standard graphics workaround for rendering transparent particle systems, bypassing the occlusion check.

### SE lens
Generating the gradient programmatically via Canvas avoids incurring a network request for a small image file. This reduces load times and allows us to parameterize the effect: we could easily change the gradient colors dynamically based on game state (e.g., green for poison, orange for fire) without needing a library of image files.

## Concept Unit: Updating CanvasTexture at runtime

### The Problem
If we have a health bar or a timer, the visual state changes constantly. Simply drawing over the canvas context does not automatically update the sprite on the screen, because the GPU has already cached the old pixels. How do we force the GPU to re-read the canvas?

### Introduce the concept in isolation
```html
<!DOCTYPE html>
<html>
<body>
<script type="module">
import * as THREE from 'three';
const canvas = document.createElement('canvas');
canvas.width = 256; canvas.height = 32;
const ctx = canvas.getContext('2d');
const texture = new THREE.CanvasTexture(canvas);
const sprite = new THREE.Sprite(new THREE.SpriteMaterial({map: texture, transparent: true}));
sprite.scale.set(2, 0.25, 1);

let health = 100;
function drawHealthBar(value) {
    ctx.clearRect(0, 0, 256, 32);
    ctx.fillStyle = '#333';
    ctx.fillRect(0, 0, 256, 32);
    const color = value > 50 ? '#00cc44' : '#cc2200';
    ctx.fillStyle = color;
    ctx.fillRect(2, 2, (value / 100) * 252, 28);
    // CRITICAL: must set needsUpdate after canvas changes
    texture.needsUpdate = true;
}
drawHealthBar(health);
console.log('texture.needsUpdate required after canvas change: true');
</script>
</body>
</html>
```
Output:
```
texture.needsUpdate required after canvas change: true
```
This is called the **needsUpdate** flag. We clear the canvas and draw a shrinking rectangle representing health. Every time we manipulate the `ctx`, we must set `texture.needsUpdate = true`. If this flag is false, Three.js assumes the texture hasn't changed and will reuse the cached texture in VRAM, causing our health bar to appear frozen.

- **`const color = value > 50 ? '#00cc44' : value > 25 ? '#ffaa00' : '#cc2200'`**
  Determines the fill color: green if above 50, yellow if above 25, red otherwise.
- **`healthCtx.fillRect(2, 2, (value / 100) * 252, 28)`**
  Draws the inner health bar. The width scales proportionally to `value / 100`.
- **`healthTexture.needsUpdate = true`**
  The crucial flag. Without this, the WebGL texture would remain fixed on its first frame.
- **`health = Math.max(0, 100 - clock.getElapsedTime() * 10)`**
  Calculates a continuously decreasing health value that stops at 0, using the clock's elapsed seconds.

### CS lens
Sending data from system RAM (the DOM Canvas) to VRAM (the GPU texture memory) is a slow operation over the PCIe bus. Three.js strictly enforces caching to avoid this overhead. `needsUpdate` is a dirty flag (a common invalidation pattern): it explicitly tells the rendering engine "this specific texture must incur the bus transfer cost on the next frame."

### SE lens
Continually redrawing a canvas every frame is expensive, even if the CPU handles it. In a real application, you would optimize this by only calling `drawHealthBar` when the `health` integer actually changes, rather than blindly rewriting the canvas inside `requestAnimationFrame`.

### The Problem
We have particles and text hovering, but they are completely static. Since a Sprite inherently rotates its geometry to face the camera, how do we make the texture itself spin or fade in and out?

### Mechanical walkthrough
- **`const t = clock.getElapsedTime()`**
  Retrieves the total time in seconds since the clock was started.
- **`sprite.material.rotation = t`**
  Spins the 2D texture applied to the sprite. At `t = Math.PI` (3.14 seconds), the texture is rotated 180 degrees.
- **`Math.sin(t)`**
  Generates a sine wave oscillating between -1 and 1 over time.
- **`Math.sin(t) * 0.5 + 0.5`**
  Shifts the sine wave range from `[-1, 1]` to `[0, 1]`.
- **`sprite.material.opacity = ...`**
  Assigns that `[0, 1]` value to the material's opacity, causing it to smoothly fade in and out without popping abruptly.

### CS lens
Material rotation happens in the fragment shader. Instead of mathematically rotating the 3D vertices of the quad, the GPU rotates the UV coordinates that map the texture onto the quad. This ensures the billboard retains its perfectly square boundary against the screen while the image inside it spins.

### SE lens
Using `Math.sin(t)` is a lightweight, stateless way to create an infinite looping animation. We do not need to keep track of state variables like "isFadingIn" or "currentOpacity"; the elapsed time alone is enough to deterministically compute the current visual state, preventing animation desynchronization bugs.
